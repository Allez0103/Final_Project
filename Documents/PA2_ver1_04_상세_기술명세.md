PA²는 STEP 완제품과 부품 파일을 분석해 분해 기반 조립 순서 초안을 추천하고, 사용자가 편집·확정한 계획을 조립 안내 영상으로 만드는 Windows 로컬 프로그램이다. 자동 추천에는 학습된 순서·방향 모델을 적용하지만, 모델은 기존 후보의 우선순위만 바꾸고 형상 간섭 판정을 대신하지 않는다.

이 명세는 기존 초기 구현 명세와 발표용 기술 설명 이후의 변경을 반영한다. 특히 사용자 지정 예외, 체결부 경로 검사 생략, 미해결 부품의 초안 보완이 있으므로 **전체 단계 생성, 사용자 확정, 정밀 경로 검증 완료를 서로 다른 상태로 관리한다.** 1_04의 외부 공유용 정확도 로그, 실제 알고리즘 사용 기록, 제품 식별 정보 제외 정책을 포함한다. 이전 명세와 원본 자료는 보존하며, 이 문서 작성으로 프로그램·DB·로그·배포 ZIP을 변경하지 않는다.

이 문서는 제품 구조와 개발 경로·동봉 모델 식별자도 다루는 내부 기술 문서다. 외부 공유용 `accuracy_log` 파일과 동일한 비식별 문서로 취급하지 않는다. 성능 자료만 외부로 전달할 때는 해당 하위 폴더의 승인된 JSON만 별도로 선택한다.

### 1.3 지원하지 않는 계산

다중 부품의 동시 이동 경로, 나사 풀림 회전, 탄성 변형, 케이블 배선, 공구 접근 공간, 체결 토크, 공차를 포함한 제조 검증, 동역학적 안정성은 계산하지 않는다. 분해 경로는 고정된 조립 원위치 형상에서 부품 하나를 직선 평행 이동하는 문제로 다룬다. 예외 부품이나 사용자 수정값을 자동으로 안전하다고 인증하지 않는다.

OCP와 Open CASCADE는 별도 경쟁 계산 엔진이 아니다. Python 코드가 OCP를 통해 C++ CAD 커널을 호출한다. STEP 해석, 질량 특성, 거리, Boolean 연산은 주로 이 네이티브 커널이 처리한다.

### 2.2 연산 위치와 병렬화

| 처리 | 실행 위치 | CPU와 GPU |
| --- | --- | --- |
| 화면 입력·위젯 갱신·편집용 VTK 표시 | Qt UI 스레드 | UI는 CPU, VTK 표시는 OpenGL 드라이버 사용 |
| 가져오기·생성·영상 업무 흐름 | `TaskWorker`와 QThread | Python 제어와 해당 네이티브 라이브러리 호출 |
| 접촉·지지·정밀 경로 검사 | 별도 CAD 프로세스의 `CadDispatcher` | Open CASCADE CPU 연산 |
| 수동 생성의 체결부 축·머리 힌트 | 업무 작업 안의 면 특징 계산 | C++ 형상 특징 계산, 경로 Boolean 없음 |
| 순서·방향 모델 추론 | 순서 생성 작업 | CPU 한 스레드 |
| 자동 재학습·평가 | 별도 유휴 작업 프로세스 | 낮은 우선순위, 한 코어, 순차 학습 |
| 영상 프레임 | 업무 작업의 오프스크린 VTK와 Pillow | 렌더링 환경에 따라 그래픽 가속, 안내 합성은 CPU |
| MP4 인코딩 | FFmpeg 프로세스 | libx264 CPU 또는 지원하는 하드웨어 인코더 |

CAD Boolean은 `OSD_ThreadPool`과 `SetRunParallel()`로 지원 연산의 CPU 스레드를 제한한다. 기본 CAD 스레드는 `max(1, min(4, CPU 수))`다. 여러 후보를 무제한 동시 검사하는 구조가 아니며 CUDA CAD 간섭 계산은 없다. 실제 그래픽 가속과 하드웨어 인코딩 가능 여부는 실행 PC의 장치와 드라이버에 달려 있다.

### 2.3 전체 호출 관계

```text
MainWindow
 ├─ ProjectService                    프로젝트 CRUD
 ├─ ImportService                     STEP·그룹·접촉·재열기
 │   ├─ AssetStore / CacheStore
 │   ├─ StepImporter / GroupingService
 │   └─ ContactService → NativeCadSession
 ├─ ModelRegistry → Planner            자동 추천
 │   └─ TwoStageSearch → evaluate → CAD worker
 ├─ ManualPlanner                     계산을 줄인 수동 초안
 ├─ ManualGroupingService / PlanService
 ├─ collect_confirmation               학습 관찰 수집과 유사도
 ├─ IdleLearningController → LearningPipeline
 └─ VideoRenderer
     └─ build_timeline → scene_at → VtkScene → Pillow → FFmpeg

공통 저장: SQLAlchemy DB + 관리 STEP + BREP 캐시 + JSON + MP4
별도 운영: RunLog → 상세 로그 → performance_summary → 외부용 정확도 로그
           SettingsStore / uninstaller
```

`MainWindow._task()`는 결과와 진행을 Qt Signal로 전달한다. 화면 모델을 갱신하는 콜백은 UI 스레드에서 처리한다. CAD 형상 객체를 프로세스 메시지로 직접 전달하지 않고, 작업 전용 binary BREP 파일과 ID·구조화된 요청으로 전달한다.

## 3 도메인 데이터와 좌표 계약

### 3.1 핵심 데이터 모델

| 모델 | 주요 필드와 의미 |
| --- | --- |
| `AtomicBody` | 원본 해시, 솔리드 인덱스, 표시명, AABB, 체적·면적·중심, 유효성, mm 단위, 대표 RGB, 배치 행렬 |
| `AssemblyGroup` | 그룹 ID, 이름, 구성 바디 ID, 부품 종류, 합성 AABB·체적·중심, 매칭 상태 |
| `ContactEdge` | 그룹 쌍, 최소 거리, 계산 근거, 접촉 정책 버전 |
| `ImportSnapshot` | 프로젝트 리비전, 입력 자산 해시, 바디·그룹·접촉, 준비 플래그와 진단 |
| `PathCheckResult` | 상태 키, 이동 그룹, 방향·거리, 판정·이유, 장애물 ID, 시간, 정책 버전, 증거 |
| `PlanStep` | 그룹 ID, 단계 번호, 분해·조립 방향, 거리, 카메라 모드·롤, 과정·자재·주의 문구, 형상 상태 |
| `Plan` | 프로젝트·스냅샷·기준 부품, 전체 그룹 ID, 단계 목록, 생성 알고리즘, 수정 여부와 상태 |
| `SceneFrame` | 특정 시각의 가시 그룹, 위치 오프셋, 강조 강도, 카메라와 안내 문구 |

`AtomicBody`는 하나의 솔리드이고 `AssemblyGroup`은 함께 움직이는 단위다. 자동 그룹과 수동 그룹 모두 순서·영상에서는 그룹 하나를 부품 하나처럼 취급한다.

### 3.2 방향과 거리

- 내부 길이는 mm, 면적은 mm², 체적은 mm³다. STEP의 mm·inch 단위를 판별하고 커널의 시스템 길이 단위를 mm로 설정한다. 단위가 불명확하면 임의로 추정하지 않고 오류 또는 명시적 단위 입력 경로로 처리한다.
- 방향은 유한한 비영 3차원 벡터이며 정규화한다. `assembly_direction = -removal_direction`이다.
- `PlanStep.validate()`는 분해·조립 벡터의 내적이 `-0.999`보다 크면 거부한다. 이동 거리는 유한하고 양수여야 한다.
- 카메라 모드는 `AUTO`, `TOP`, `BOTTOM`, `FRONT`, `BACK`, `LEFT`, `RIGHT`이며 화면 롤은 별도 값이다. 화면 회전이 실제 부품의 배치나 조립 방향을 바꾸지 않는다.
- ID의 논리적 범위와 DB PK의 범위를 구분한다. 바디·그룹 DB PK는 보통 `<스냅샷 ID>:<논리 ID>`로 저장해 스냅샷별 기록 충돌을 방지한다.

### 3.3 판정과 초안 상태

| 분류 | 값 | 해석 |
| --- | --- | --- |
| 경로 판정 | `PASS` | 해당 상태·방향·정책에서 경로가 허용됨. 예외 적용 여부는 증거를 함께 확인 |
| 경로 판정 | `BLOCKED` | 교차 등의 차단 근거가 확인됨 |
| 경로 판정 | `UNKNOWN` | 계산 실패·제한 시간·보수 영역 불확실성 등으로 증명하지 못함 |
| 경로 판정 | `NOT_TESTED` | 사용자 예외·수동 지정·체결부 배치 등 경로를 계산하지 않음 |
| 계획 상태 | `COMPLETE` | 검색의 경로·지지 기준을 만족한 결과 |
| 계획 상태 | `REVIEW_REQUIRED` | 전체 단계여도 예외·지지 미확인·체결부 지정·미해결 보완 등이 포함된 편집용 결과 |
| 기타 계획 상태 | `PARTIAL`, `NO_SOLUTION_WITHIN_BUDGET`, `CANCELLED`, `FAILED` | 부분 결과·예산 종료·취소·실패 |

단계의 `geometry_status`에는 `AUTO_CHECKED`, `SUPPORT_UNVERIFIED`, `INITIAL_REGION_EXCEPTION`, `INITIAL_DECREASE_EXCEPTION`, `GEOMETRY_REPAIRED`, `FASTENER_ASSIGNED`, `DRAFT_UNRESOLVED`, `MANUAL_ASSIGNED`, `USER_COLLISION_EXCEPTION`, `USER_CONFIRMED_UNCHECKED` 등이 있다. 원래 생성 근거는 최초 생성 기록에 보존한다. 사용자가 수정한 계획을 확정해도 정밀 검증 상태로 승격하지 않는다.

## 4 프로젝트 저장과 데이터베이스

### 4.1 파일과 DB의 분리

기본 데이터 루트는 `%LOCALAPPDATA%\THN\PA2`다. `PA2_DATA_ROOT`가 있으면 해당 경로가 우선한다. DB는 별도 URL이 없으면 로컬 SQLite `database/pa2-dev.sqlite3`다. `PA2_DATABASE_URL`을 통한 다른 연결 코드도 있지만, 이 배포의 기본 운영과 검증은 SQLite 기준이며 사내 공통 학습 서버를 제공하는 것은 아니다.

```text
사용자 데이터 루트
 ├─ database/pa2-dev.sqlite3
 ├─ assets/<SHA256>/source.step 또는 source.stp
 │                     └─ manifest.json
 ├─ cache/shape/<캐시 키>/scene.json
 │                         ├─ bodies/*.binbrep
 │                         └─ complete.json
 ├─ projects/<프로젝트 ID>/planning/*.json
 │                         └─ videos/*.mp4
 ├─ jobs/                       CAD 임시 스냅샷과 작업 상태
 ├─ learning/bundles/<모델 ID>/model.txt + manifest.json
 │           ├─ cycles/<주기 ID>/snapshot.json 등
 │           └─ last-idle-result.json
 ├─ logs/                       사용자 데이터 영역의 내부 로그
 ├─ settings.json
 └─ .pa2-owned.json              제거용 소유 등록

설치 폴더
 ├─ PA2.exe / uninst.exe / _internal
 ├─ .pa2-install.json
 └─ log/                        EXE 옆의 상세 생성·확정·학습·이벤트 JSON
     └─ accuracy_log/           외부 공유용 성능·유사도·알고리즘 요약 JSON
```

사용자 데이터의 `logs`와 EXE 옆 `log`는 서로 다른 위치다. STEP·BREP·MP4를 DB의 대용량 BLOB에 넣지 않고, 해시와 ID, 상대 경로로 연결한다. 실행용 리소스는 frozen 환경의 `_MEIPASS`, 설치 루트는 EXE 위치를 기준으로 하며 시험용 경로 재지정은 운영 경로와 분리한다.

### 4.2 프로젝트와 자산

`ProjectService.create()`는 프로젝트명·차종·품종의 빈 값을 거부하고 기존 분류가 있으면 재사용한다. 프로젝트 목록은 차종·품종·이름으로 정렬하고 삭제 표시가 없는 항목을 반환한다. 프로젝트 삭제는 `deleted_at`을 기록하는 논리 삭제이며 공유 자산을 즉시 지우지 않는다. 이는 `uninst.exe`의 관리 데이터 물리 삭제와 다르다.

`AssetStore.ingest()`는 원본을 1 MiB 단위로 읽어 SHA-256을 계산하고 관리 사본을 만든 뒤 사본 해시를 다시 확인한다. 같은 내용은 같은 해시 저장소를 사용한다. 원래 경로와 이름은 프로젝트 자산 관계에 별도로 보존한다. 형상 보정이나 그룹화는 외부 원본 STEP를 다시 저장하지 않는다.

### 4.3 실행 경로의 주요 테이블

| 영역 | 테이블 | 핵심 저장 내용과 연결 |
| --- | --- | --- |

| 입력 | `assets`, `project_assets` | 자산 해시·경로·크기, 프로젝트별 역할·원본명·원본경로·리비전 |
| 분석 | `import_snapshots`, `atomic_bodies` | 입력 해시, 준비 상태·진단, 바디별 기본 특성 |

| 평가와 이력 | `evaluations`, `model_activations` | 비교 결과, 이전·이후 모델 조합과 활성화 사유 |

`plan_steps.camera_json`에는 카메라 모드와 `roll_deg`가 들어간다. 처음 생성한 초안과 현재 편집본을 같은 레코드로 취급하지 않는다. 확정본은 `plan_steps`를 나중에 다시 읽어 재구성하지 않고 저장 당시 JSON에서 읽는다.

```text
Project
 ├─ ProjectAsset → Asset → 관리 STEP
 ├─ ImportSnapshot → Body / Group / Contact / GroupingStructure
 └─ Plan → PlanStep
      ├─ Generation                  최초 초안과 계산 근거

           └─ 프로젝트 영상 파일

ModelBundle ← ActiveModel / LearningCycle / Evaluation / ModelActivation
```

위 그림은 논리적 관계다. 모든 ID 참조에 SQL 외래키가 선언돼 있다는 뜻은 아니다. `shape_definitions`, `occurrences`, `static_features`, `asset_refs`, `jobs`, `job_events`, `cache_entries`, `settings_versions`, `videos` 같은 보조 스키마도 있으나 현재 GUI 주 경로에서 모두 채우는 것은 아니다. 예를 들어 영상 생성은 확정 ID를 포함한 관리 파일명과 파일 탐색으로 연결하고, 색상은 BREP 캐시의 바디 메타데이터를 복원한다.

`Database.session()`은 성공 시 commit, 예외 시 rollback한다. `initialize()`는 누락 테이블과 활성 모델 슬롯을 생성하지만 임의의 모든 기존 컬럼 변경을 자동 마이그레이션하는 기능은 아니다.

### 4.4 캐시와 재열기

캐시 키는 단계, 입력 해시, 단계 버전, 관련 설정, 캐시 스키마를 정규화한 JSON의 SHA-256이다. 형상 키는 STEP 자산 해시, `StepImporter.VERSION`, 단위 설정 등을 사용한다. 캐시는 임시 디렉터리에 작성한 뒤 `complete.json`을 만들고 완료 경로로 공개한다. 완료 마커가 없는 항목은 복원 대상으로 보지 않는다.

`save_scene()`은 바디별 binary BREP와 체적·AABB·RGB·배치 정보가 들어 있는 `scene.json`을 저장한다. `ImportService.reopen()`은 현재 스냅샷·그룹·접촉·그룹 트리·관리 자산·BREP 캐시를 결합해 작업을 복원한다. 캐시가 없거나 손상되면 외부 원본이 아니라 관리 STEP에서 재생성한다. 복원이 곧 자동 순서 재생성이나 재학습을 뜻하지는 않는다.

## 5 STEP 분석과 부품 그룹화

### 5.1 입력 처리 흐름

```text
MainWindow._analyze
 → ImportService.prepare
   → AssetStore.ingest
   → 캐시 복원 또는 StepImporter.read
   → GroupingService.resolve
   → ContactService.build
   → 분석 스냅샷과 진단 저장
 → ModelEditor.set_result
```

`StepImporter.read()`는 `STEPControl_Reader.ReadFile()`, 단위 판별, `TransferRoots()`를 수행하고 솔리드를 순회한다. 각 솔리드에 대해 `BRepBndLib.AddOptimal_s()`로 AABB, `BRepGProp.VolumeProperties_s()`와 `SurfaceProperties_s()`로 체적·면적·체적 중심을 계산한다. 가져오기 단계는 `BRepCheck_Analyzer(shape, False)`를 사용한 기본 유효성을 확인한다. 경로 검사에서 수행하는 기하 일관성 정밀 검사는 이보다 엄격하다.

모든 바디가 정확히 한 그룹에 소속되는 분할 조건을 지킨다. 읽을 수 없는 파일, 단위 불명, 형상 없음, 불완전 접촉 그래프는 진단을 남긴다. 초기 간섭 체적은 현재 구현에서 모든 부품 쌍에 대해 미리 전수 저장하는 것이 아니라 방향 힌트와 경로 검사의 관련 쌍에서 계산한다.

### 5.2 자동 매칭

자동 그룹은 부품 STEP의 솔리드 구성을 완제품의 바디 구성과 대조해 만든 이동 단위다. 제조상의 의미를 이해해 모든 최소 조립단위를 자동 발견하는 기능은 아니다.

1. 바디 수가 많은 부품 정의부터 비교한다.
2. 체적·면적과 정렬된 AABB 크기를 기존 상대 오차로 비교한다.
3. 여러 바디를 가진 부품은 바디 사이 중심 거리와 배치 일관성을 확인한다.
4. 중복 소유 없이 수용한 바디를 이후 후보에서 제외한다.
5. 모든 기존 매칭을 끝낸 뒤 아직 미매칭인 바디만 완화 재시도한다.
6. 추가 회전 불변 특징으로 회전된 미매칭 후보를 재시도한다.
7. 끝까지 유일하게 식별하지 못한 바디는 별도 그룹과 미매칭·모호 진단으로 남긴다.

상대 비교의 기본 형태는 `|a-b| ≤ max(|a|, |b|, 1) × 상대 허용치`다. 기존 상대 허용치는 `1e-4`, 즉 0.01%이며 가져오기에서 사용하는 위치 허용치는 모델 크기로 계산한 `geometry_epsilon_mm`다.

완화 재시도의 허용치는 상대 0.1%와 위치 0.005mm다. 해당 정의의 후보가 하나이고 다른 정의와 바디 소유 경쟁이 없을 때만 수용한다. 이미 매칭된 그룹을 다시 풀거나 전체 부품에 완화 값을 일괄 적용하지 않는다. 이 허용치는 **그룹화용**이며 간섭 epsilon을 늘리지 않는다.

회전 재시도는 관성 행렬 고유값, 면의 종류와 면적, 모서리 종류와 길이, 다중 바디 배치의 비교 자료를 사용한다. 임의의 두 형상이 완전히 합동임을 증명하는 절차가 아니므로 모호한 경우 자동 병합하지 않는다.

### 5.3 파일명 종류 분류

기존 규칙인 `MBD-`, `PLT-`, `BLK-`, `BUS-`, `RLY-`, `COV-`, `SEL-`, `AIR-`, `BLT-`, `NUT-`, `HVSC ...`, `LV CONT`를 유지한다. 추가로 토큰 경계를 가진 `BOLT_`, `SCREW_`, `NUT_`, `HOUSING_`, `HSG_`, `CARRIER_`, `BUSBAR_`, `RELAY_`, `GASKET_`, `VENT_`, HV·LV 커넥터 별칭 등을 처리한다.

임의의 문자열 일부가 비슷하다는 이유로 분류하지 않는다. 대응 종류가 없는 퓨즈·PCB·저항 등은 `UNKNOWN` 일반 부품으로 남길 수 있다. `UNKNOWN`은 입력 실패나 볼트라는 뜻이 아니다. 일반 부품과 체결부를 나누는 기준은 `PartType.BOLT`와 `PartType.NUT`다.

### 5.4 STEP 대표색

`apply_step_colors()`는 기존 STEP 작업 세션을 공유하는 `STEPCAFControl_Reader`와 XCAF 스타일을 사용한다. 원래 형상 읽기 순서를 바꾸거나 색상을 위해 CAD를 다시 저장하지 않는다. 솔리드·부품 스타일을 우선하고 면 색상만 있으면 면적 투표로 대표색을 정한다. 여러 바디 그룹도 유효 RGB의 면적 가중 투표로 색 하나를 선택한다. 색이 없으면 그룹 ID에 따른 결정적 기본색을 쓴다.

면별 다색 렌더링을 보존하는 것이 아니라 **부품당 대표색 한 가지**를 표시한다. 색 추출은 형상·경로 판정과 독립이며 실패가 임의 형상 보정의 근거가 되지 않는다.

### 5.5 수동 그룹과 해제

`ManualGroupingService.change()`의 계약은 다음과 같다.

- 현재 루트 그룹을 두 개 이상 선택해 그룹화한다. 이름은 직접 입력하거나 선택된 부품 이름 중에서 고르며 길이는 1~120자다.
- 그룹 창에는 분해 방향 설정이 없다. 그룹 구성을 먼저 확정한 뒤 자동·수동 순서를 생성하면서 방향을 정한다.
- 자동 분석으로 만들어진 그룹은 하나의 잠긴 부품이며 내부 바디 단위로 해제하지 않는다. 사용자가 만든 수동 그룹만 한 수준 해제해 원래 멤버를 복원한다.
- 기준 부품은 그룹화·해제 대상에 넣지 않는다. 필요하면 먼저 기준을 변경한다.
- 그룹은 바디 ID 합집합과 합성 AABB·체적·중심을 사용한다. 종류가 섞이면 `UNKNOWN`이며 볼트·너트만 묶어도 `UNKNOWN` 일반 부품으로 취급해 경로 생략을 잘못 적용하지 않는다.
- 기존 접촉 그래프를 원래 그룹에서 새 그룹으로 재매핑하고 내부 간선을 제거한다. 원래 그래프를 보존하므로 해제 시 원래 외부 연결을 복원할 수 있다.
- 새 스냅샷과 프로젝트 리비전을 만든다. 기존 확정본은 보존하지만 현재 초안·확정 참조를 비워 순서 재생성과 재확정을 요구한다.

그룹화는 단순한 화면 폴더가 아니라 이동·탐색 단위의 변경이다. 자동 생성에서 새 그룹의 `part_type`과 합성 형상으로 계산한다. 수동 편집 도중 그룹을 바꾼 뒤 이전 순서를 그대로 확정하거나 영상으로 만들지 않는다.

## 6 자동 조립 순서 추천

### 6.1 현재 기본 알고리즘

```text
현재 활성 모델 조합 고정
 → 접촉 그래프 완전성 및 정책 확인
 → 기준 부품 결정과 체결부 연결 그래프 준비
 → 사용자 예외를 분해 선두에 배치하고 장애물에서 제외
 → 체결부 축·머리 힌트 준비
 → 체결부를 뺀 일반 부품 집합에서 경로 탐색
 → 확인한 접두 순서 보존, 미해결 부품의 편집용 단계 보완
 → 연결 일반 부품 앞에 체결부 분해 단계를 삽입
 → 전체 분해 순서 반전, 방향 부호 반전
 → 조립 초안과 최초 생성 기록 저장
```

호출은 `MainWindow._generate()` → `ImportService.ensure_contacts()` → `ModelRegistry.provider()` → `Planner.generate()` → `TwoStageSearch.run()` → `RemainingSetSearch.visit()` 순서다. 소스에 이전 가상 체결부 탐색 클래스가 남아 있지만, 기본 2단계 경로는 일반 부품 검색 결과를 그대로 사용하고 체결부를 나중에 삽입한다.

기준 부품은 사용자가 지정한 유효 그룹을 사용한다. 엔진에 지정이 없으면 예외를 제외한 유효 체적 그룹 중 가장 큰 부품을 선택한다. 기준은 이동 단계에서 제외하고 장애물과 지지 기준으로 남는다.

### 6.2 일반 부품 우선순위

모델이 없거나 사용할 수 없을 때는 `ExteriorPriorityProvider`의 AABB 노출도 힌트를 사용한다. 각 축 방향에 대해 AABB를 방향 축과 직교 화면 평면에 투영하고 전방 장애물의 투영 겹침을 합산한다.

```text
투영 구간 중심 = bounds.center · 축
투영 반폭 = Σ |축 성분 i| × bounds.size[i] / 2
방향 coverage = Σ 전방 장애물과의 투영 겹침 면적 / 대상 투영 면적
```

coverage와 전방 장애물 수가 작은 방향을 외부에 더 노출된 방향으로 본다. 부품 정렬에는 여섯 방향의 최소 점수, +Z 방향 점수, coverage 합, ID를 사용한다. 이는 정확한 가시면적이나 분해 성공 확률이 아니다. 활성 순서 모델은 이 후보를 점수 내림차순으로 재정렬하며, 완료한 일반 부품 순서를 후삽입 단계에서 다시 바꾸지 않는다.

### 6.3 일반 부품의 방향 후보

기본 후보는 `+Z, -Z, +X, -X, +Y, -Y` 여섯 축이다. `policy_hint()`는 현재 남아 있는 접촉 이웃만 이용한다.

- 초기 교차가 있으면 최대 접촉면 법선을 억지로 확정하지 않고 노출도 순서를 사용한다.
- 적절한 평면 접촉이 있으면 평면 간 교차 면적으로 가장 큰 접촉을 찾고 그 면에서 멀어지는 법선을 우선한다.
- 노출도와 접촉 법선은 방향 순서의 힌트다. 그 자체로 경로를 통과시키지 않는다.
- 활성 방향 모델이 있으면 기존 여섯 방향을 다시 정렬한다. 학습으로 검사 방향을 추가하거나 나머지 방향을 삭제하지 않는다.
- 한 방향이 경로와 해당 지지 정책을 통과하면 즉시 해당 부품 제거를 채택한다. 같은 남은 집합으로 가는 다른 통과 방향은 다시 탐색하지 않는다.

설정의 `max_directions=24`는 확장·기존 방향 경로를 위한 항목이며, 현재 기본 2단계 일반 부품 경로가 24방향을 모두 검사한다는 뜻은 아니다.

### 6.4 이동 거리

단위 분해 방향을 `d`, 움직이는 AABB의 꼭짓점 집합을 `M`, 나머지 AABB 합집합의 꼭짓점 집합을 `R`이라 두면 `exit_distance()`는 다음을 계산한다.

```text
pmin = min(p · d), p ∈ M
rmax = max(r · d), r ∈ R
L = max(0, rmax - pmin) + exit_clearance_mm
```

단순히 모든 부품에 같은 이동 거리를 쓰지 않고 남은 형상과 방향에 맞춰 바깥으로 벗어나는 거리를 구한다. 거리가 충분하다는 AABB 계산은 중간 경로의 무간섭 증명이 아니다.

### 6.5 볼트와 너트의 연결 및 후삽입

`fastener_attachments()`는 접촉 그래프에서 체결부끼리 연결된 사슬을 따라가 일반 부품 대상을 찾는다. 볼트와 너트의 간접 연결도 사용한다. 직접 연결된 일반 부품이 없으면 기준 부품 부착으로 처리한다.

자동 생성에서는 연결 대상 중 **분해 순서가 가장 빠른 일반 부품** 앞에 체결부 분해 단계를 둔다. 전체를 조립 순서로 뒤집으면 공유 체결부는 관련 일반 부품들이 조립된 뒤에 위치한다. 사용자 예외도 같은 연결 대상에 포함되므로 관련 체결부는 예외 부품을 제거하기 전에 배치한다.

체결부 자체는 경로 검사하지 않는다. 방향은 `assigned_direction()`에서 다음 순서로 결정한다.

1. 볼트에 신뢰할 머리 방향이 있으면 머리 쪽 축 방향.
2. 너트에 축이 있고 기존 접촉으로 연결된 볼트의 머리와 축이 식별되면 볼트 머리에서 멀어지는 축 부호.
3. 나머지는 축의 두 부호 중 연결 대상 중심에서 멀어지는 쪽.
4. 축이 없으면 여섯 축 중 중심에서 멀어지는 쪽. 부호 동률은 +Z, +Y, +X 성분 순으로 결정한다.

`_fastener_hint()`는 긴 원통면으로 샤프트 축을 찾고 넓은 축방향 면·동축 원통의 면적과 관성 특성으로 머리 쪽을 판단한다. 새로운 접촉·Boolean·경로 검사를 하지 않는다. 결과는 `FASTENER_ASSIGNED`와 `NOT_TESTED`로 기록하며 일반 화면에 불필요한 미검증 문구를 반복하지 않더라도 내부 근거를 없애지 않는다.

### 6.6 사용자 지정 예외

예외는 이름 하드코딩이 아니라 현재 스냅샷의 그룹 ID 목록으로 저장한다. 자동 생성에서 예외를 분해 선두에 두고 노출도 기준 첫 방향을 채택하며, 이후 경로·지지 장애물에서 제외한다. 상태는 `USER_COLLISION_EXCEPTION`, 경로 판정은 `NOT_TESTED`다. 조립 역순에서는 예외가 뒤쪽에 온다. 예외가 있는 결과는 검토용이다.

LV CONT, HVSC 2800, AIR-BENT 같은 이름은 사용자가 특정 프로젝트에 지정한 예이며 모든 프로젝트의 기본 예외가 아니다. 기준과 예외는 같은 그룹에 동시에 지정할 수 없다.

### 6.7 지지 관계

경로 통과 뒤 남은 일반 부품이 기준·테이블에서 지지 경로를 갖는지 `support_check()`로 확인한다. 기준 그룹과 원래 모델의 최저 Z에 접한 그룹을 초기 지지 집합으로 두고, 확인한 상하 접촉 간선을 따라 지지를 전파한다. 단순 접촉 간선이 곧 지지 간선은 아니다.

기본값 `allow_support_unknown_draft=True`이면 경로가 통과했지만 지지를 증명하지 못한 단계는 `PATH_CLEAR_SUPPORT_UNVERIFIED`로 수용한다. 이 경우에도 검토 필요를 기록한다. 지지 검사는 정역학적 질량·마찰·체결·외부 지그를 완전히 해석하는 물리 시뮬레이션이 아니다.

### 6.8 미해결 부품과 탐색 중단

정상 종료나 예산 종료로 일반 부품을 전부 검증하지 못하면 확인한 접두 순서는 보존한다. 남은 부품을 현재 우선순위와 노출도 방향으로 배치하고 `DRAFT_UNRESOLVED`를 기록한다. 이전 BLOCKED·UNKNOWN 결과의 인덱스를 진단에 연결하며 새 PASS를 만들지 않는다. 이어 체결부를 삽입해 가능한 한 전체 편집 초안을 만든다.

따라서 `draft_complete=True`와 `search_complete=True`는 다르다. 사용자가 취소한 경우에는 `_planned()`가 결과를 새 초안으로 저장하지 않고 기존 초안을 유지한다. 접촉 그래프 자체가 불완전한 경우에는 자동 생성 전에 접촉 보완을 시도하고 여전히 미완료이면 오류로 종료한다.

### 6.9 중복 탐색 감소

| 캐시 | 키와 재사용 조건 |
| --- | --- |
| 상태 방문 | 남은 그룹의 `frozenset`, 제거 접두 순서가 달라도 같은 원위치 장애물 집합이면 동등 상태 |
| 부품 평가 | 남은 집합과 그룹 ID, 완료한 평가만 재사용 |
| 전체 경로 | `state_key`, 그룹, 방향, 거리. 같은 진단 인덱스를 재사용해 중복 시간 합산 방지 |
| 차단 증거 | 같은 부품·방향, 차단 상대가 아직 남아 있고 두 경로가 상대의 전체 투영 구간을 벗어나는 경우 |
| 쌍 검사 | 두 형상, 경계, 방향·거리, epsilon, 예외 정책이 같은 경우 |
| Boolean 체적 | 원래 형상 핸들의 동일성과 이동 벡터까지 확인 |
| 이동 영역·방향 힌트 | 면·방향·거리, 또는 그룹과 남아 있는 접촉 이웃 |

`closed` 상태는 해당 정책에서 완전히 탐색한 상태만 등록한다. 예산·취소·되돌림 제한으로 일찍 중단한 상태를 물리적으로 분해 불가능하다고 저장하지 않는다. 상태 동등성은 현재의 고정 원위치·한 부품 직선 이동 가정에 의존하며 미래의 중간 배치가 남는 탐색에는 그대로 확장할 수 없다.

## 7 정밀 형상 검사와 최적화

### 7.1 BREP와 AABB의 역할

BREP는 면·모서리·정점 및 곡면 정의로 구성된 경계 표현이다. 화면용 삼각형 메시와 구분한다. 정밀 검사에는 원래 BREP 또는 허용 범위 안에서 보정한 계산 사본을 쓴다.

AABB는 축에 평행한 경계상자로 `(xmin, ymin, zmin, xmax, ymax, zmax)`를 가진다. 부품 AABB와 끝점 AABB의 합집합은 직선 이동의 전체 경로를 감싸는 상자다. 이 상자가 장애물과 분리되면 해당 쌍의 정밀 계산을 생략할 수 있다. 상자가 겹친다는 사실만으로 실제 충돌이라고 판단하지는 않는다.

접촉 계산은 `ContactService.build()`에서 gap만큼 확대한 AABB로 후보를 줄인 뒤 실제 BREP 쌍의 거리 계산을 수행한다. 거리 `≤ contact_gap_mm`이면 접촉 간선을 만든다. 기본 gap은 0.05mm다. 알 수 없는 쌍이 남으면 접촉 그래프를 완전하다고 표시하지 않는다.

### 7.2 연속 경로 검사

`ConservativePathChecker.check()`의 주요 흐름은 다음과 같다.

1. 이동 형상과 장애물의 기하 유효성 및 계산 사본 보정 여부 확인.
2. 전체 이동 AABB가 분리된 쌍 제외.
3. 초기 위치의 교차 체적과 예외 적용 조건 확인.
4. 비예외 경로에서 모든 관련 경계면의 이동 영역을 검사.
5. 정확한 이동 영역의 교차로 BLOCKED, 보수 영역만 겹치거나 생성 실패이면 UNKNOWN 또는 추가 증명 시도.
6. 종점의 실제 분리 거리 확인.

`BRepAlgoAPI_Common`으로 교차 형상을 만들고 `BRepGProp.VolumeProperties_s()`로 체적을 읽는다. 교차 체적 `> epsilon³`를 실제 침투 근거로 사용한다. `BRepExtrema_DistShapeShape`는 실제 형상 사이 거리를 계산한다. Boolean은 비파괴 옵션으로 계산하고 완료·결과 유효성을 확인한다. 결과가 잘못되면 인수 역순 재시도와 제한된 파라미터 보정을 시도하며, 여전히 무효이면 체적 숫자만 믿고 PASS 처리하지 않는다.

표면 이동 영역은 `BRepPrimAPI_MakePrism` 등으로 만든다. 평행 이동과 나란한 평면이나 축방향 원통면은 관련 경계 통과가 없음을 이용해 제외할 수 있다. 불명확한 이동 영역에 대한 위치 표본은 충돌을 입증하는 데 사용할 수 있지만, 표본에서 안 겹친다는 사실만으로 일반 경로 PASS를 만들지 않는다.

양의 거리 기반 보완은 평행 이동 거리 함수의 1-Lipschitz 성질을 사용한다. 구간 `[a,b]`의 중점 거리 `Dmid > (b-a)/2 + epsilon`이면 그 구간 전체가 분리됨을 증명할 수 있다. 증명하지 못하면 구간을 나누고, 최소 간격이나 예산에 도달하면 UNKNOWN이다.

### 7.3 초기 겹침 정책

기본 설정은 모든 부품 초기 영역 예외와 겹침 감소 예외가 켜져 있다. 처음 겹치지 않은 상대는 연속 경로 검사를 유지한다. 처음부터 겹친 상대만 다음 검토용 정책으로 처리한다.

```text
V0 = 초기 교차 체적
체적 허용 폭 δV = max(epsilon³, V0 × 10⁻⁶)
검사 위치 = 0, 0.01, 0.05, 0.1, 0.25, 0.5mm, 이후 최대 0.5mm 간격
각 위치의 V(t) ≤ 지금까지의 최소 체적 + δV 조건 확인
```

최대 256개 위치를 확인한다. 최저 체적보다 다시 커지면 `OVERLAP_REINCREASE`로 차단한다. 겹침이 `epsilon³` 이하로 줄면 그 지점 이후의 연속 경로와 원래 상대에 대한 종점 분리를 검사한다. 계산 실패, 아직 겹친 종점, 표본 예산 초과는 UNKNOWN이다.

이 방법은 연속적인 단조 감소나 동일 상대 내부의 새로운 국소 간섭을 완전히 배제하지 못한다. 한 영역의 겹침 증가가 다른 영역의 더 큰 감소에 가려질 수 있고 표본 사이의 재증가도 놓칠 수 있다. 따라서 `continuous_monotonicity_proven=False`, `same_pair_local_collision_excluded=False`와 검토 상태를 남긴다. “초기 겹침을 전부 무시한다” 또는 “새 간섭을 모두 배제했다”고 설명하지 않는다.

감소 예외를 끄고 초기 영역 예외만 켜면 계산용 장애물에서 초기 이동 형상을 뺀 `O′ = O \ M(0)`에 대해 전체 이동 영역을 검사하는 기존 방식으로 돌아간다. 이때도 원래 장애물에 대한 종점 분리를 확인한다. 모든 부품 예외가 꺼진 경우에만 기존 볼트 축방향 초기 겹침 정책이 별도 적용된다.

### 7.4 계산용 파라미터 보정

가져오기 기본 유효성 검사와 `BRepCheck_Analyzer(shape, True)`의 정밀 검사는 다르다. 토폴로지는 유효하지만 에지 파라미터의 기하 일관성이 맞지 않으면 계산 단계에서 실패할 수 있다.

`prepare()`는 원래 형상을 복사하고 `BRepLib.SameParameter_s()`로 파라미터 일관성을 보정한다. 수용 조건은 모두 만족해야 한다.

| 항목 | 수용 기준 |
| --- | --- |
| 보정 전 토폴로지 | 유효해야 함 |
| 보정 후 정밀 기하 | 유효해야 함 |
| 최대 형상 허용오차 | 0.01mm 이하 |
| AABB 변화 | 해당 모델의 geometry epsilon 이하 |
| 에지·면·정점 수 | 변화 없음 |
| 체적 변화 | `max(10⁻⁹, 보정 전 체적 × 10⁻⁵)`mm³ 이하 |

상대 체적 변화 한도 `10⁻⁵`는 0.001%다. 보정 중 체적 값이 조금 달라질 수 있으나 의도적으로 부품을 크게 만들거나 간섭을 통과시키기 위한 팽창이 아니다. 이 수용 한도는 간섭 epsilon과 독립이며 원본 STEP에는 반영하지 않는다. 수용 근거는 `input_repairs` 진단으로 전달한다.

### 7.5 BSpline과 보수 분할

정확한 Prism 생성은 완료 여부, 유효성, 유한 솔리드 방향, 양의 체적을 확인한다. BSpline 등에서 이를 증명하지 못하면 전체 UV 영역을 덮는 패치와 이동 경계상자로 보완한다. 원통·원뿔의 U는 각도로 처리할 수 있지만 일반 곡면의 U와 V는 임의 파라미터이므로 동일하게 라디안 분할하지 않는다.

일반 곡면은 기본적으로 U와 V 각각 네 구간을 사용하고, 생성 패치 수는 최대 128개로 제한한다. 보수 패치가 장애물과 분리되면 해당 영역은 안전하지만 보수 패치의 교차만으로 실제 충돌이라고 확정하지 않는다. 정확한 위치의 교차 증거나 연속 거리 증명을 추가로 확인하며 끝내 증명하지 못하면 UNKNOWN을 유지한다.

### 7.6 복잡한 형상에 대한 선택적 보수 프록시

현재 최적화는 영상용 외형이나 원래 BREP에서 내부 면을 삭제하는 단순화가 아니다. 정확한 형상을 유지하며 계산 제외를 증명하는 공간 자료와 캐시를 추가한다.

- 면 수 1,000개 이상, 또는 면 수 500개 이상이고 비평면 면 비율이 20% 이상인 형상에 우선 적용한다.
- 원래 유효 솔리드의 면 경계를 보수적으로 감싼 BVH를 만든다.
- 질의 상자가 어떤 경계도 만나지 않고 원래 솔리드 분류기의 대표점 판정이 OUT이면, 연결된 상자 전체가 바깥임을 이용해 교차 계산을 생략한다.
- 평면 트림과 곡면 UV의 보수 범위는 내부 구멍·빈 공간을 임의로 채운 실물 형상으로 대체하는 것이 아니다.
- 실패·모호·부적격이면 원래 Boolean과 sweep 검사로 복귀한다. 프록시만으로 BLOCKED나 불확실한 PASS를 만들지 않는다.

Common 체적 LRU, 방향의 평면·접촉쌍 캐시, sweep 캐시 확대도 적용한다. 활성화 시 sweep 엔트리는 최대 2,048개이고 보수 영역 기록 수는 4,096개로 제한한다. 체적 캐시는 8,192개, 쌍 판정 캐시는 4,096개 한도다. 모델과 프록시가 서로 다른 최적화임을 구분한다. 전자는 검사 순서를, 후자는 동일 검사의 계산량을 바꾼다.

## 8 수동 생성과 순서 편집

### 8.1 수동 생성

`MainWindow._generate_manual()` → `ManualPlanner.generate()`는 현재 부품 목록의 일반 부품 순서를 **조립 순서**로 사용한다. 일반 부품의 기본 분해 방향은 +Z, 조립 방향은 -Z이며 이동 거리는 AABB로 계산한다. 기존 접촉 그래프를 재사용하고 접촉 갱신이나 일반 부품 경로·지지 탐색을 새로 하지 않는다.

볼트·너트는 연결 대상 중 조립 순서가 가장 늦은 일반 부품 뒤에 둔다. 체결부 축·머리 계산은 유지한다. 예외 상태는 보존하지만 자동 모드의 예외 선두 분해 탐색 정책을 수동 목록에 강제로 적용하는 경로는 아니다. 결과는 `MANUAL_ASSIGNED`, `FASTENER_ASSIGNED`, `USER_COLLISION_EXCEPTION`을 포함한 `REVIEW_REQUIRED`이며 경로 호출과 경로 Common 수는 0이다.

### 8.2 편집 화면

상단 공통 영역은 PA² 아이콘, 프로그램명, 작업 취소, 설정, 학습 현황이다. 화면은 프로젝트, 모델·순서, 영상의 세 탭이다. 자동 추천과 순서 편집이라는 두 기능 구조는 같은 모델·순서 탭에 있다.

| 위치 | 기능 |
| --- | --- |
| 모델·순서 상단 | 자동생성, 수동생성 |
| 왼쪽 흰 카드 | 부품 목록·검색·Ctrl/Shift 다중 선택·수동 그룹화·해제 |
| 가운데 | 3D 모델, 회전·이동·맞춤·시점·확대·숨기기 도구, 모델 애니메이션 재생 |
| 오른쪽 흰 카드 | 기준·예외 지정, 분해 방향·거리, 카메라와 90도 좌우 롤, 과정·자재·주의, 미리보기와 적용 |
| 아래 | 형상 미리보기 순서 카드, 다중 선택·묶음 이동, 실행 취소·다시 실행, 순서 확정 |

LIVE3D 문구와 상단 검은 테두리는 제거했다. 부품 목록·작업 속성 제목은 흰 카드 안에 있고 위쪽 여백을 확보한다. 일반 사용자 화면에서 순서 생성 진단 버튼은 숨기지만 계산 근거와 기록은 유지한다. 주요 버튼의 화면색은 승인된 `#2633C5`다. 인쇄 PANTONE 색상과 모니터 RGB의 완전한 색 일치를 보증하는 것은 아니다.

### 8.3 선택 표시와 표시 전용 보정

부품 목록·3D 선택·순서 카드는 그룹 ID로 연결한다. 단일 일반 클릭으로 같은 부품을 재선택하면 선택을 해제하고, 기존 Ctrl/Shift 다중 선택 동작은 유지한다. 선택 그룹은 빨강과 opacity 1, 나머지 보이는 그룹은 회색 `(0.65,0.65,0.65)`으로 바꾼다.

| 선택 상태 | 비선택 opacity | 의미 |
| --- | ---: | --- |
| 단일 선택 | 0.25 | 투명도 75% |
| 다중 선택 | 0.10 | 투명도 90% |

다중 선택은 나머지 부품을 무조건 숨기지 않는다. 사용자가 직접 숨긴 부품은 선택만으로 다시 나타나지 않는다. 내부 선택은 별도 렌더 레이어로 식별하고 작은 체결부 등에는 위치를 찾기 위한 작은 표시 오프셋과 연결선을 사용할 수 있다. 이 보정은 화면 상태만 바꾸며 CAD 원위치·순서·저장 변환·영상 이동에는 적용하지 않는다. 선택 해제와 단계 미리보기 종료 시 원래 표시 속성을 복원한다.

### 8.4 순서와 속성 변경

`SequenceCards`의 ID 목록을 `Plan.steps`와 대응시켜 재배열하고 `step_index`를 다시 부여한다. 여러 단계를 선택해 내부 순서를 유지한 채 묶음 이동한다. 속성 수정은 현재 선택 단계에 적용하며 과정 문구의 후속 단계 일괄 적용도 지원한다. 편집 이력은 화면 내부 실행 취소·다시 실행 스냅샷으로 관리하고 초안은 자동 저장한다.

사용자 순서·방향 수정은 **CAD 간섭 재검사·차단·자동 보정을 수행하지 않는다.** 다만 방향 정규화, 양의 거리, 중복·누락·기준 부품 포함 여부 같은 데이터 계약 검사는 유지한다. “검사 생략”은 잘못된 데이터 형식까지 수용한다는 뜻이 아니다.

### 8.5 미리보기와 확정

작업 속성의 미리보기는 현재 입력값을 계획 사본에 적용하고 `build_timeline()`과 `scene_at()`로 선택 단계의 방향·시점·롤을 보여준다. 저장된 계획을 몰래 덮어쓰거나 경로를 재검사하지 않는다.

`PlanService.save_generated()`는 최초 생성본을 한 번 저장한다. 이후 편집 저장은 최초 생성 JSON을 덮어쓰지 않는다. `confirm()`은 검증된 데이터 구조와 사용자가 수용한 계획을 `confirmations`에 JSON으로 고정한다. 사용자가 수정한 단계는 예외를 제외하고 `USER_CONFIRMED_UNCHECKED`로 구분한다.

`content_signature()`는 기준, 그룹, 입력 스냅샷, 순서, 방향, 거리, 카메라와 롤, 안내 문구, 변환 등을 정규화한 해시다. 영상 생성 시 현재 편집본과 확정본이 일치해야 하고 미적용 속성이 없어야 한다. 수정했다면 다시 확정해야 한다. 초안 저장 버튼이나 별도 재검토 버튼 없이 초안 자동 저장과 영상 생성 버튼을 사용한다.

## 9 학습 모델과 데이터 수집

### 9.1 두 모델의 역할

| 모델 | 한 번의 질의 | 현재 입력 행렬 | 출력 | 적용 대상 |
| --- | --- | --- | --- | --- |
| 순서 모델 | 남은 상태에서 다음 제거 후보 비교 | 일반 부품 후보 수 N × 44개 특징 | 후보별 실수 점수와 정렬된 그룹 ID | 일반 부품 후보의 검사 순서 |
| 방향 모델 | 한 일반 부품의 여섯 방향 비교 | 6 × 52개 특징 | 방향별 실수 점수와 정렬된 방향 벡터 | 기존 여섯 방향의 검사 순서 |

두 모델 모두 `LGBMRanker`이며 `objective=lambdarank`를 사용한다. 전체 조립 순서를 한 번에 출력하거나 성공 확률을 출력하는 분류기가 아니다. 현재 상태의 후보 사이 상대 순위를 학습하고 점수를 내림차순으로 정렬한다. 동점은 기존 기하 우선순위를 유지한다.

```text
남은 일반 부품 상태
 → FeatureBuilder.rows
 → 순서 모델 scores
 → 검사할 부품 선택
 → 방향 기본 순서와 direction_rows
 → 방향 모델 scores
 → ConservativePathChecker
 → 첫 통과 방향 수용
 → 남은 상태 갱신 후 반복
```

사용자 예외, 기준 부품, 체결부 후삽입 정책은 모델이 대체하지 않는다. 체결부 방향도 이 방향 모델 대신 별도의 축·머리 계산을 사용한다. 학습 모델 오류가 자동 생성 전체의 실패로 이어지지 않도록 이전 검증 모델이나 규칙으로 복귀한다.

### 9.2 순서 입력 특징 44개

정규화 기준 `D`는 초기 전체 AABB 대각선, `V`는 초기 전체 그룹 체적 합, `N0`는 초기 전체 그룹 수다. 동적 특징은 현재 남은 집합과 접촉 그래프로 다시 계산한다.

| 특징 범주 | 필드 | 계산 또는 현재 값 |
| --- | --- | --- |
| 범주 2개 | `part_type`, `product_type` | 매니페스트의 범주 인덱스, 모르는 값은 UNKNOWN |
| 크기 3개 | `bbox_x`, `bbox_y`, `bbox_z` | AABB 세 크기를 내림차순 정렬한 값 / D. 이름과 달리 고정 세계축 크기가 아님 |
| 체적과 면적 2개 | `volume`, `area` | 그룹 체적 / V, 현재 area는 결측 |
| 중심 3개 | `center_x`, `center_y`, `center_z` | 그룹 중심에서 초기 전체 AABB 중심을 뺀 성분 / D |
| 형상 비율 2개 | `aspect_max_mid`, `aspect_mid_min` | 정렬한 최대/중간, 중간/최소 크기 |
| 축과 평면 5개 | `axis_abs_x/y/z`, `has_axis`, `planar_area_ratio` | 현재 축 성분·평면 비율은 결측, has_axis는 0 |
| 기준 관계 4개 | `base_distance`, `touches_base`, `base_hops`, `base_reachable` | 중심 거리 / D, 직접 접촉 여부, 접촉 그래프 BFS 거리와 도달 여부 |
| 접촉 2개 | `contact_count`, `contact_ratio` | 남은 이웃 수, 이웃 수 / max(N0-1,1) |
| 이웃 종류 13개 | `neighbors_<PartType>` | 종류별 남은 이웃 수 / max(N0-1,1) |
| 남은 상태 3개 | `remaining_ratio`, `removed_ratio`, `remaining_volume_ratio` | 남은 수 / N0, 제거 수 / N0, 남은 체적 / V |
| 지지 3개 | `supporter_count`, `on_table`, `has_support_path` | 현재 FeatureBuilder에서는 결측 |
| 유효성 2개 | `volume_valid`, `geometry_valid` | 체적 정보 존재와 기본 기하 유효성 |

스키마에 필드가 있다고 모든 형상 특성이 계산되어 입력되는 것은 아니다. 위 결측 필드는 현재 그대로 NaN으로 변환한다. 별도의 축 검출·지지 계산이 존재해도 이 44개 입력 행렬에 모두 연결된 것은 아니다. 열 순서는 모델 매니페스트의 `feature_names`와 정확히 맞춰야 한다.

### 9.3 방향 입력 특징 52개

기본 44개에 아래 8개를 추가한다.

| 필드 | 의미 |
| --- | --- |
| `direction_x/y/z` | 후보 방향 성분 세 개 |
| `exposure_coverage`, `exposure_obstacles` | 해당 방향의 AABB 투영 가림 합과 장애물 수 |
| `contact_away_mean`, `contact_away_min` | 현재 접촉 이웃으로부터 멀어지는 방향 투영 거리 / D의 평균과 최소 |
| `directed_size` | `Σ |d_i| × AABB 원래 축 크기_i / D` |

이 특징 계산은 현재 저장된 기본 정보와 접촉 관계를 사용한다. 후보 여섯 방향의 순위를 얻기 위해 정밀 경로 검사를 여섯 번 선행 실행하지 않는다.

### 9.4 수집되는 데이터와 라벨

`MainWindow._confirm()`은 `PlanService.confirm()` 이후 `collect_confirmation()`을 호출한다. 추가 사용자 입력 없이 확정 순서·분해 방향·예외 목록·그룹·접촉·생성 모드·최초 생성 지표·사용자 수정 유사도·원래 경로 근거를 수집한다.

| 데이터 | 학습에서의 의미 |
| --- | --- |
| 사용자 확정 순서와 방향 | 사용자 선호 라벨. 물리적 경로 PASS가 아님 |
| 사용자 지정 예외 부품 | 전체 확정 선호에 포함. 예외가 하나 있다는 이유로 프로젝트 전체를 버리지 않음 |
| 체결부 | 관찰과 확정본에 보존하지만 일반 부품 순위 학습 후보에서는 제외 |
| 원래 PASS와 BLOCKED | 원래 남은 집합·방향·거리·정책에 묶인 계산 근거로 보존 |
| UNKNOWN과 NOT_TESTED | 물리적 성공·실패 라벨로 변환하지 않음 |
| 자동·수동 생성 및 수정 후 확정 | 선호 관찰로 수집 가능. 수동 생성도 정밀 경로 검증으로 간주하지 않음 |

현재 LGBMRanker 두 모델은 선호 라벨을 학습하며 물리적 충돌 분류 라벨을 학습하지 않는다. 초기 겹침 감소 같은 조건부 PASS도 원래 정책과 증거를 함께 해석해야 한다.

일반 순위 학습은 확정 조립 순서를 뒤집어 제거 상태를 재현하는 teacher forcing 방식이다. 각 상태의 다음 선택은 1, 다른 후보는 0이다. 외부 참고 라벨의 같은 작업에 속한 여러 부품은 동률 양성으로 보존하고 임의의 내부 순서를 정답으로 만들지 않는다.

방향 학습은 확정 방향이 여섯 축 중 하나와 1도 이내인 경우에만 6개 후보 중 해당 방향을 1로 둔다. 임의 사선 방향을 가까운 축으로 무조건 반올림하지 않고 관찰에는 남기되 해당 축 라벨 학습에서 제외한다.

### 9.5 중복과 형상 계열

정확한 재확정 중복 서명에는 프로젝트 ID, 형상 계열, 기준, 바디 구성, 순서, 방향, 예외 여부가 들어간다. 카메라·문구만 바뀐 재확정은 새로운 순서 사례를 무조건 늘리지 않는다. 공통 주기 데이터는 프로젝트별 최신 유효 완전 확정 관찰을 선택한다. 한 프로젝트를 여러 번 확정해도 재학습 프로젝트 수는 하나다.

`family_fingerprint()`는 바디의 반올림한 체적, 정렬한 크기, 바디 중심 쌍의 거리 목록을 해시한다. 이름 변경·전체 평행 이동·수동 그룹 변경에 덜 민감하게 중복 계열을 식별하려는 방법이다. 실제 제조 품종을 완전 자동 분류하는 모델이 아니다. 품종은 프로젝트의 분류 입력이고 형상 계열은 데이터 분리용 기하 지문으로 서로 다르다.

품종마다 모델을 별도로 고르는 구조가 아니라 로컬 저장소의 공통 모델 조합을 사용한다. 동봉 모델의 대표 학습 품종은 HVJB이며 알려지지 않은 품종은 범주 UNKNOWN으로 입력한다. 다른 품종에서도 실행할 수 있다는 것과 추천 품질이 검증됐다는 것을 구분한다. 사내 여러 PC의 데이터는 자동 합쳐지거나 중앙 서버로 전송되지 않는다.

### 9.6 동봉 모델과 초기 적용

| 역할 | 동봉 모델 ID |
| --- | --- |
| 순서 | `1e17b860-aa06-5b8e-9d06-7deaca782bed` |
| 방향 | `8a2cf202-7fc0-561d-a21d-324b03347a5d` |

배포 리소스에는 모델 두 개, 학습 참고 라벨 55개, 고정 평가 라벨 5개와 평가용 BREP가 들어 있다. 기존 45개 합성 변형은 공통 계보 한 계열, 추가 학습용 10개는 각각의 구조 계열로 관리해 동봉 모델의 학습 계열은 11개다. 이 참고 라벨은 실제 사용자 확정이나 공장 승인된 물리적 PASS 데이터로 가장하지 않는다.

`bootstrap()`은 두 번들의 호환성과 체크섬을 먼저 검증하고 사용자 `learning/bundles`에 복사해 등록한다. 활성 조합이 비어 있을 때만 초기 조합으로 적용하고 `seed-v28` 표식을 저장한다. 기존 활성 모델을 덮어쓰지 않으며, 사용자가 복원한 뒤 매 실행마다 동봉 모델을 다시 켜지 않는다. 이 시점까지의 유효 프로젝트를 신규 10개 집계의 기준선으로 잡는다.

`PreferenceModel`은 역할, 번들 스키마, 입력 스키마, LightGBM 주 버전, 파일 체크섬, 범주와 특징 열 순서·개수를 검증한다. 순서 스키마는 `features-v1`, 방향 스키마는 `direction-features-v1`, 번들 스키마는 `model-bundle-v21`이다. 예측 결과의 길이와 유한성도 확인한다.

### 9.7 모델 학습 설정

```text
objective = lambdarank             metric = ndcg
label_gain = [0, 1]                n_estimators = 300
learning_rate = 0.05               num_leaves = 15
min_child_samples = 20             random_state = 20261017
n_jobs = 1                        deterministic = True
force_col_wise = True
```

`LearningPipeline._fit()`는 `LGBMRanker.fit(X, labels, group=질의별 후보 수, sample_weight=계열 가중치, categorical_feature=범주 열)`를 호출한다. 전체 질의 수를 Q, 계열 수를 F, 해당 계열 질의 수를 Qf라 하면 같은 질의 행에 `Q/(F×Qf)` 가중치를 적용한다. 반복 변형이 많은 한 계열이 질의 개수만으로 전체 학습을 지배하는 것을 줄인다.

모델은 `model.tmp`에서 `model.txt`로 완료하고 매니페스트에 특징·범주·학습 설정·데이터 digest·학습 사례·보류 계열·동률 정책·체크섬을 기록한다. 학습했다고 즉시 활성 슬롯을 바꾸지는 않는다.

## 10 자동 재학습과 모델 교체

### 10.1 실행 조건과 주기

`IdleLearningController`는 앱 실행 중 500ms 주기로 상태를 확인한다. 사용자 입력 후 기본 120초가 지났고 전경 작업·모델 재생·단계 미리보기·영상 재생이 없을 때 학습을 고려한다. 설정에서 자동 학습과 평가 통과 모델의 자동 적용을 각각 켜거나 끌 수 있다. 새 기본값은 둘 다 True이며 기존 사용자가 저장한 False는 유지한다.

초기 동봉 모델 적용 이후에는 다음 기준을 사용한다.

```text
신규 수 = 현재 유효 완전 확정 프로젝트 ID 집합 - 기준선의 프로젝트 ID 집합
신규 수 ≥ retrain_new_projects(기본 10개) → 공통 주기 시작
```

변형 제품도 별도 프로젝트로 확정되면 포함하지만 한 프로젝트 재확정은 추가 집계하지 않는다. 최초 모델이 없는 경우의 30계열·1,000개 상태 조건과 이전 24시간·5계열·500개 상태 항목은 초기·기존 호환 경로에 남아 있으며, 동봉 모델 이후의 정상 10개 주기를 추가로 막는 기준으로 사용하지 않는다.

UI 쪽은 저장 관찰의 고유 프로젝트 수로 가볍게 준비 여부만 확인하고 실제 작업에서 완전성·고정 평가 제외 등 유효 조건을 다시 검사한다. 따라서 입력 수와 실제 학습에 들어가는 사례 수는 같지 않을 수 있다.

### 10.2 순차 실행과 재개

```text
WAITING
 → RUNNING: 데이터·설정·기준 모델 조합 스냅샷 고정
 → 순서 모델 학습 및 저장
 → 방향 자료 기준 확인, 충분하면 방향 모델 학습 및 저장
 → 저비용 선호 평가
 → 유망 후보만 실제 CAD 비교
 → READY 또는 REJECTED
 → READY는 조건 재확인 후 APPLIED

사용자 작업·예산 종료: PAUSED 또는 미완료 체크포인트에서 재개
오류: FAILED / 설정·기준 모델 변경: STALE
```

방향 모델은 기본 총 100개 방향 사례, 두 개 이상 축, 해당 축별 10개 이상 조건을 사용한다. 부족하면 방향 모델만 보류하고 순서 후보와 기존 방향 조합을 평가할 수 있다. 두 모델을 동시에 학습하는 것이 아니라 동일 데이터 스냅샷으로 순서 다음 방향을 학습한다.

유휴 프로세스는 낮은 우선순위, 한 코어 affinity, 수치 라이브러리 스레드 1을 사용한다. 기본 예산은 1,800초, 합계 메모리 한도는 1,536MiB다. 별도 OS 파일 잠금으로 동시에 여러 학습 작업이 실행되는 것을 막는다. 부모 PID와 생성 시각을 확인해 앱 종료 뒤 학습 자식이 남는 것을 방지한다.

사용자 입력 시 협조 취소 후 응답하지 않는 해당 작업 트리를 종료한다. 이미 저장된 모델·평가 실행 체크포인트는 재사용하되, 중단된 한 번의 긴 fit 호출 내부 상태를 그대로 복원하는 것은 아니다. 설정 정책 서명이나 기준 모델 조합이 바뀌면 이전 주기를 그대로 승격하지 않고 STALE로 처리한다.

READY와 REJECTED는 완료한 데이터 기준선을 갱신한다. FAILED·중단은 기준선을 소비하지 않는다. 개선 없는 완료 주기는 같은 10개를 매번 다시 학습하지 않고 이후 신규 프로젝트를 기다린다.

### 10.3 학습과 평가 자료 분리

`expanded_snapshot()`은 로컬 확정 관찰과 동봉 학습 참고 자료를 결합한다. 고정 평가 E01부터 E05는 학습에서 제외하고, 같은 자산 해시나 등록된 평가 계열 지문을 가진 로컬 복제본도 학습에 섞지 않는다. 라벨 파일의 체크섬과 실제 평가 BREP 파일의 해시도 확인한다.

로컬 형상 계열은 정렬한 목록의 `local_families[::5]`를 보류 평가 계열로 추가한다. 같은 계열의 상태를 학습·평가에 무작위로 나누지 않는다.

이 정책에는 현재 알려진 제한이 있다. 신규 프로젝트가 같은 한 계열뿐이면 그 계열 전체가 평가용으로 남아 신규 10개가 모두 학습에서 빠질 수 있다. 따라서 **10개 추가로 주기가 실행됐다는 사실만으로 그 10개가 실제 fit에 포함됐다고 판단하지 않는다.** 최신 구현에서는 이 분리 정책을 변경하지 않았으며 학습 사례 ID와 보류 계열 목록으로 실제 반영 여부를 확인해야 한다.

### 10.4 저비용 1차 평가

기존 조합, 새 순서만, 새 방향만, 둘 다 새 모델인 조합을 비교한다. CAD 없이 탐욕적 후보 순위와 첫 추천 방향을 투영해 다음 지표를 평가한다.

- 일반·예외 제외 부품의 선후 일치율.
- 실제 다음 부품을 1순위로 추천한 비율.
- 첫 추천 방향과 선호 방향의 일치율.

평균은 먼저 같은 계열의 사례를 평균한 뒤 계열 평균을 동일하게 평균한다. 세 지표의 하락이 기본 1%p 이내이고 적어도 하나가 `10⁻⁶`을 넘게 개선된 조합만 실제 CAD 비교로 보낸다. 모두 같으면 개선 후보 없음으로 REJECTED 처리한다. 이는 실제 생성 속도가 더 나빴다는 판정이 아니다.

### 10.5 실제 CAD 비교와 최종 교체 기준

실제 비교는 같은 저장 BREP, 접촉 정책, 기준·예외, 계산 설정으로 기본 두 번 반복하고 실행 순서를 번갈아 배치한다. CAD Boolean 스레드는 비교 중 1로 고정한다.

| 조건 | 기본 기준 |
| --- | --- |
| 사례별 단계 수와 경로 검증 수 | 기존보다 감소하지 않음 |
| 사례별 미해결·미판정·시간 초과·오류 | 기존보다 증가하지 않음 |
| 사례별 선후 유지율 | 5%p 초과 하락 없음 |
| 계열 평균 순서·방향 선호도 | 각각 기존 대비 1%p 이내 하락 |
| 시간·경로 호출·후보 수 비율 | 각각 계열 평균에서 기존 대비 1.05 이하 |
| 개선 필요 조건 | 순서 또는 방향 3%p 이상 개선, 또는 시간이나 경로 호출 10% 이상 감소 |

마지막 개선 조건만 만족한다고 나머지 유지 조건을 무시하지 않는다. `promotion_gate()`를 통과한 조합을 READY로 두고 `ModelRegistry.promote()`가 현재 설정·기준 조합·모델 무결성을 다시 확인한 뒤 두 슬롯을 한 트랜잭션에서 교체한다. 학습 도중인 기존 생성 작업은 시작할 때 고정한 모델 조합을 사용한다. 새 적용은 다음 생성부터 반영하며 기존 확정본과 영상은 바꾸지 않는다.

### 10.6 복귀와 운영 확인

모델 파일 손상, 스키마 불일치, 범주·특징 불일치, 비유한 예측값은 이전 검증 조합으로 복귀할 수 있다. 이전 조합도 없으면 기존 규칙을 사용한다. 검증되지 않은 순서·방향 모델을 임의로 혼합해 복구하지 않는다. 학습 현황 화면에서 활성 모델, 주기 결과, 실패 이유, 확정 유사도를 보고 이전 조합 복원이나 평가 통과 후보 적용을 할 수 있다.

추론 장애 시의 규칙 복귀와 후보 평가를 구분한다. 새 후보 평가 중 모델 오류는 기존 규칙으로 조용히 바꾸어 좋은 후보처럼 평가하지 않고 해당 평가를 실패시킨다.

## 11 추천 유사도와 실행 로그

### 11.1 확정본 비교 지표와 계산 범위

`PlanService.analyze_confirmation()` → `compare_orders()`는 최초 생성본과 사용자 확정본에 공통으로 존재하는 그룹 ID를 비교한다. 전체, 일반부품, 예외를 제외한 일반부품으로 범위를 나눠 각 범위의 순서를 따로 구성한다.

| 범위 키 | 비교 대상 |
| --- | --- |
| `all` | 체결부·예외를 포함한 공통 그룹 |
| `general` | `PartType.BOLT`, `PartType.NUT`를 제외한 공통 일반부품 |
| `general_without_exceptions` | 일반부품 중 지정 예외와 예외 상태인 그룹을 추가 제외 |

기준 부품은 이동 단계에 없으므로 보통 비교 대상에 포함되지 않는다. 수동 그룹도 그룹 하나가 비교 단위다. 어떤 실제 부품이 일반부품으로 분류되는지는 현재 그룹의 `part_type`에 따라 달라진다.

```text
공통 비교 그룹 수 = n
전체 비교 쌍 수 P = n(n-1)/2
preserved_pairs = 최초 초안의 선후관계가 확정본에서도 유지된 쌍 수
pair_order_ratio = preserved_pairs / P
lcs_ratio = 두 순서의 최장 공통 부분수열 길이 / n
direction_agreement = 방향 차이가 1도 이하인 그룹 수 / n
방향 각도 = acos(clamp(분해 방향의 내적, -1, 1))
```

방향 벡터는 계획 데이터 계약에서 정규화되어 있다. 실제 비교 함수는 부동소수 오차를 줄이기 위해 내적을 [-1,1]로 제한한다. 비교 쌍이 0이면 선후 일치율은 `null`, 비교 부품이 0이면 LCS·방향 비율도 `null`이다. 표본이 없다는 이유로 0%나 100%를 임의로 채우지 않는다.

선후 일치율은 같은 절대 순번에 있는 부품의 비율이 아니다. 한 부품을 앞뒤로 이동하면 여러 쌍의 선후가 동시에 달라진다. LCS도 연속된 부분 문자열이 아니라 내부 순서를 보존하는 최장 부분수열이다. 추가·제거 그룹은 상세 비교에 ID 목록으로, 외부 요약에는 개수로만 보존한다.

최초 생성본이 없는 과거 프로젝트는 현재 편집본을 가짜 원본으로 삼지 않는다. 사용자가 수정·확정해도 최초 초안이 없으면 해당 비교는 불가다.

모든 비교값은 **사용자 확정본과 초안의 선호 유사도**다. 물리적 간섭 정답률, 안전도, 공장 승인율이나 LGBM의 예측 성공 확률이 아니다. 사용자가 잘못 확정한 순서도 선호 데이터가 될 수 있다.

### 11.2 상세 로그와 외부용 요약의 분리

```text
PA2_ver1/
 ├─ PA2.exe
 └─ log/
     ├─ generation_<생성 ID 또는 시도 ID>.json
     ├─ generation_<생성 ID>.lck
     ├─ learning_<주기 ID>.json
     ├─ event_<이벤트 ID>.json
     └─ accuracy_log/
         └─ accuracy_<독립 UUID v4의 hex>.json
```

다른 생성 실행은 다른 파일에 저장한다. 같은 최초 생성 계획을 여러 번 편집·확정하면 같은 파일의 `confirmations[]`에 버전이 누적된다. 확정 ID가 같은 재분석은 새 버전을 만들지 않는다. 실제 사용자 로그는 배포 ZIP에 넣지 않으며 최초 압축 해제 시 `log/accuracy_log`는 비어 있다.

설치 루트는 frozen 실행 시 EXE 위치, 소스 실행 시 소스 프로젝트 루트이며 `PA2_INSTALL_ROOT` 시험용 재지정을 지원한다. `PA2_DATA_ROOT`의 사용자 데이터 영역과 다르다. 이 폴더에 쓰기 권한이 필요하다.

| 파일 종류 | 스키마 | 저장 성격 |
| --- | --- | --- |
| 생성 상세 | `pa2-generation-log-v1` | 최초 초안·설정·부품·내부 ID·시간·확정본·비교의 로컬 원문 |
| 학습 상세 | `pa2-learning-log-v1` | 주기당 최신 상태·단계·집계·설정·기존 모델·결과·오류 |
| 모델 이벤트 | `pa2-event-log-v1` | 초기 적용·활성화·복귀별 시각과 원문 상세 |
| 외부용 성능 | `pa2-accuracy-log-v1` | 식별 정보 없는 허용 지표와 고정 알고리즘 정보 |

상세 로그의 주요 필드는 다음과 같다.

| 필드 | 내용 |
| --- | --- |
| `generation_id`, `plan_id`, `snapshot_id` | 내부 식별자. 외부용 파일에는 복사하지 않음 |
| `project`, `parts` | 프로젝트명·차종·품종·리비전, 부품명·종류 |
| `generation_mode`, `settings`, `metrics` | 실행 모드·설정과 원래 전체 성능 지표 |
| `native_activity_counts` | 반환된 native path 계산 근거의 활동 카운터 |
| `algorithm_observations` | 반환된 CAD 근거에서 추출한 `shape_proxy_enabled`, `shape_proxy_version` |
| `stage_seconds_inclusive`, `stage_times_overlap` | 포함 관계가 있는 세부 시간 |
| `initial_plan`, `initial_available` | 덮어쓰지 않는 최초 생성본과 존재 여부 |
| `accuracy`, `confirmations` | 최근 비교 및 버전별 확정 ID·시각·계획·비교 |
| `accuracy_report_id` | 독립 외부 요약과의 대응용 난수. 로컬에서만 원래 생성 ID와 연결 |

`algorithm_observations`는 native 경로 증거에서 얻은 값이 모두 한 값일 때 저장하고 혼재하거나 없으면 미상으로 둔다. 새로운 형상 계산을 실행하거나 원래 경로 판정을 바꾸지 않는다.

실패·취소 시도는 `attempt_id`, 모드·상태·경과 시간·메시지를 상세 로그에 기록할 수 있다. 외부용 파일에서는 임의 메시지와 오류 원문을 제외한다. 과거 프로젝트 확정은 생성 ID가 없고 최초 계획이 `null`일 수 있다.

### 11.3 생성·확정·요약의 함수 호출 흐름

```text
자동 Planner 또는 ManualPlanner 결과
 → MainWindow._planned
 → PlanService.save_generated
     ├─ 현재 초안 저장
     ├─ plan_generations에 최초 결과 1회 저장
     └─ safe_log → RunLog.generated
          → _save_with_accuracy
              ├─ 독립 accuracy_report_id 준비
              ├─ 로컬 상세 JSON 원자적 저장
              └─ performance_summary → accuracy_log JSON 원자적 저장

사용자 확정
 → PlanService.confirm → confirmations의 계획 스냅샷
 → RunLog.confirmed → 확정 이력 추가, 아직 비교 없으면 비교 불가
 → collect_confirmation / analyze_confirmation
 → compare_orders → 비교 저장
 → RunLog.confirmed → 같은 확정 이력의 비교 보완
 → 같은 외부 요약의 accuracy / confirmations 갱신
```

원래 초안·실행 지표·알고리즘 근거는 생성 시점의 값을 사용한다. 사용자가 나중에 순서를 수정하거나 활성 모델이 교체됐다고 과거 실행의 알고리즘을 현재 설정으로 바꾸지 않는다. 모델과 로그는 독립 저장 자료이며 요약 JSON을 외부로 보내는 기능이 자동 업로드나 학습 서버 연동을 의미하지 않는다.

### 11.4 외부용 JSON의 루트 계약

외부 요약은 원문에서 필드를 삭제하는 블랙리스트가 아니라 **허용된 필드로 새 객체를 구성하는 화이트리스트**다.

| 루트 키 | 형식 | 의미 |
| --- | --- | --- |
| `schema_version` | 고정 문자열 | `pa2-accuracy-log-v1` |
| `report_id` | 문자열 | 프로젝트·생성·확정·모델 ID와 별도로 만든 UUID v4 hex |
| `generation_mode` | 열거 | `auto`, `manual`, `unknown` |
| `status` | 고정 상태 | 확인한 원래 상태 또는 `GENERATED`, `CONFIRMED`, `UNAVAILABLE` |
| `performance` | 숫자·불리언 객체 | 수집되고 유효한 허용 성능 필드만 |
| `accuracy` | 객체 | 최근 확정 비교, 비교의 성격과 불가 사유 |
| `confirmations` | 객체 배열 | 1부터 시작하는 익명 버전 번호와 당시 비교 지표 |
| `algorithms` | 객체 | 고정 알고리즘·버전·실제 사용과 최적화 정보 |

원래 상태 허용 목록은 `COMPLETE`, `REVIEW_REQUIRED`, `PARTIAL`, `NO_SOLUTION_WITHIN_BUDGET`, `CANCELLED`, `FAILED`다. 임의 오류 문자열을 상태로 복사하지 않는다. `CONFIRMED`는 사용자가 수용했다는 뜻이며 물리 검증 완료는 아니다.

`accuracy`에는 `available`, `scopes`, `kind=user_confirmation_similarity_not_physical_accuracy`, `physical_accuracy=false`, `direction_tolerance_deg=1`을 둔다. 비교 불가 사유는 원문 대신 `NO_BASELINE`, `NOT_CONFIRMED`, `COMPARISON_UNAVAILABLE` 중 하나다.

각 scope의 허용 필드는 다음과 같다.

| 필드 | 형식과 의미 |
| --- | --- |
| `count`, `pair_count`, `preserved_pairs` | 비교 부품 수·비교 쌍 수·유지한 쌍 수 |
| `lcs_length`, `lcs_ratio` | 공통 부분수열 길이와 0~1 비율 |
| `direction_same`, `direction_changed`, `direction_agreement` | 방향 유지·변경 개수와 0~1 비율 |
| `pair_order_ratio` | 선후 유지 0~1 비율 |
| `added_count`, `removed_count` | scope 밖 비교 객체 수준의 추가·제외 개수. 원래 ID는 제외 |

`confirmations[]`의 각 항목은 `version`, `available`, `scopes`와 수집된 추가·제외 개수만 가진다. 확정 ID·시각·실제 계획은 들어가지 않는다. `accuracy`는 최신 확정의 비교를 대표하고, 이전 버전의 비교는 배열에서 보존한다.

### 11.5 성능 지표의 허용 목록과 집계 단위

| 허용 필드 | 정의와 주의 |
| --- | --- |
| `generation_wall_sec` | GUI 생성 요청부터 결과 수신까지. 접촉 보완·모델 준비 등이 포함될 수 있음 |
| `elapsed_sec` | Planner 또는 수동 생성기 내부 시간 |
| `native_path_elapsed_sec` | native path 요청의 누적 경과 시간 |
| `direction_hint_elapsed_sec`, `skeleton_elapsed_sec` | 방향 힌트와 일반부품 초안 탐색 시간 |
| `tested_candidates` | 새로 기록한 남은 상태·부품·방향·거리 후보 수. 고유 부품 수가 아님 |
| `native_path_calls`, `actual_native_path_calls`, `virtual_native_path_calls` | 경로 worker 호출과 실제·가상 검사 집계. 접촉·지지·방향 힌트 요청과 구분 |
| `pair_calculations`, `brep_common_calls` | 경로 계산에서 반환된 부품 쌍 계산과 Common 활동 수 |
| `brep_common_cache_hits`, `pair_cache_hits`, `exact_path_cache_hits`, `blocked_witness_cache_hits` | 서로 다른 수준의 계산 근거 재사용 |
| `unique_states`, `closed_states`, `state_visits` | 고유·완료·방문 상태 수 |
| `closed_state_skips`, `duplicate_group_skips`, `backtracks` | 중복 상태·부품 건너뜀과 되돌림 |
| `completed_groups`, `total_moving_groups` | 생성 단계와 기준을 제외한 전체 이동 그룹 수 |
| `verified_path_steps`, `unresolved_general_steps` | 경로 확인 단계와 미해결 보완 단계 |
| `fastener_assigned_steps`, `collision_exception_steps` | 경로 없이 지정한 체결부·사용자 예외 단계 |
| `unknown_count`, `blocked_count`, `native_timeout_count` | 경로 후보 기록의 미판정·차단·시간 초과 수 |
| `direction_hint_calls` | 방향 힌트 계산 횟수 |
| `draft_complete`, `path_complete`, `search_complete` | 초안 완성·전체 경로 정책 통과·탐색 완료를 구분하는 불리언 |

수집되지 않은 성능 필드는 원칙적으로 생략한다. 카운터는 bool이 아닌 0~2⁶³-1 정수, 시간은 bool이 아닌 0~10¹²의 유한한 수만 허용한다. 비율은 0~1의 유한한 수 또는 `null`, 플래그는 실제 bool만 받는다. 문자열 숫자, NaN, Infinity, 음수 카운터와 임의 중첩 객체는 외부 성능 필드에 넣지 않는다.

후보 → 경로 요청 → 부품 쌍 → 면·Boolean은 중첩된 계산 수준이다. 이 네 수를 더해 총 검사 횟수라고 하지 않는다. 포함 관계가 있는 시간을 더해 전체 생성 시간으로 보고하지 않는다. 강제 종료된 native 호출은 중간 카운터를 반환하지 못할 수 있으므로 Common 집계가 프로그램 전체 모든 연산의 완전한 총계라고 보장하지 않는다.

### 11.6 알고리즘 기록의 의미와 버전 계약

`accuracy_log._algorithms()`는 원래 `initial_plan.source_algorithm`, `metrics.learning_models`, native 활동 카운터와 `algorithm_observations`에서 고정 정보만 뽑는다. 모델 ID를 외부에 남기지 않고 다음을 구분한다.

| 필드 | 허용 값·계산 |
| --- | --- |
| `planner` | `two_stage_general_first`, `manual_list_order`, `exterior_general_first`, `target_fastener`, `default_priority`, `unknown` |
| `planner_version` | 아래 고정 목록과 정확히 일치하는 버전만, 그 외 `null` |
| `recommendation_scope` | `general_parts_only` |
| `order_recommendation` | 순서 추천의 method·성공 prediction_calls·fallback_occurred |
| `direction_recommendation` | 방향 추천의 같은 세 필드 |
| `fastener_direction` | 식별 가능한 계획이면 `geometry_axis_head_rule`, 아니면 `unknown` |
| `shape_optimization` | method·version·enabled·applied |

계획 버전 허용 목록은 다음과 같다. 과거 코드 경로도 해석할 수 있도록 목록에 둔 것이며 모든 항목이 현재 GUI 기본 경로라는 뜻은 아니다.

```text
general-first-fastener-insertion-v16 → two_stage_general_first
two-stage-learned-priority-v21      → two_stage_general_first
manual-v20-list-order              → manual_list_order
exterior-virtual-fastener-v1       → exterior_general_first
target-fastener-v1                → target_fastener
default                          → default_priority
```

역할별 추천 method는 다음 계약을 따른다.

| method | 조건 |
| --- | --- |
| `LGBMRanker` | 해당 역할의 저장된 성공 예측 횟수가 양수 |
| `LGBMRanker_with_fallback` | 성공 예측이 있으며 저장된 모델 오류·복귀 근거도 있음 |
| `rule_based` | 해당 역할의 성공 예측이 0으로 관측됐거나 알려진 규칙 계획 |
| `manual_fixed` | 식별된 수동 목록/고정 방향 생성 |
| `unknown` | 버전·예측 실행 근거가 불충분 |

활성 모델이 등록되어 있다는 이유만으로 실제 사용했다고 기록하지 않는다. 남은 후보가 한 개라 순서 모델을 호출하지 않았으면 순서 역할은 규칙 기반일 수 있다. 한 실행에서 순서만 모델을 쓰고 방향은 규칙을 쓰는 경우도 각각 구분한다.

`prediction_calls`는 부품 수가 아니라 성공한 모델 scores 호출 수다. 복귀 제공자도 모델을 사용하면 중첩 `fallback` 기록의 성공 횟수를 합산한다. 최대 16단계까지만 순회하고 임의 실패 원문이나 모델 번들 정보를 복사하지 않는다. `fallback_occurred`는 저장된 비어 있지 않은 failures 목록의 존재를 나타내며, 기록이 없는 과거 실행에서 모든 종류의 오류가 전혀 없었음을 증명하는 값은 아니다. 복귀 대상은 이전 검증 모델 또는 규칙일 수 있다.

형상 최적화의 계약은 다음과 같다.

- method는 식별되면 `selective_conservative_proxy`, 수동 경로 검사는 `not_applicable`, 근거가 없으면 `unknown`이다.
- 현재 허용 버전은 `boundary-bvh-outside-proof-v1` 하나다. 임의 형상·프로젝트·모델 문자열을 버전으로 출력하지 않는다.
- `enabled`는 반환된 CAD 실행 증거의 활성화 값이다. 명시적인 프록시 활동이 있으면 활성화 실적을 확인할 수 있다.
- `applied=true`는 `PROXY_FACE_SWEEP_CLEAR` 또는 `PROXY_ENCLOSURE_CLEAR`가 양수인 경우로, 해당 실행에서 원래 교차 계산을 생략한 실적을 뜻한다.
- 프록시 활성화 또는 생성 시도만으로 applied를 true로 만들지 않는다. 활성화가 명시적으로 false, 경로 호출이 0, 수동 생성이거나 완전한 카운터에 생략 실적이 없으면 false로 판별할 수 있다.
- 중단 등으로 카운터가 빠져 확정할 수 없으면 `null`이다. 수동 생성은 enabled와 version을 `null`, applied를 false로 둔다.
- 이전 로그에 생략 활동만 있으면 enabled/applied는 복원 가능해도 버전은 `null`일 수 있다. 현재 환경의 `PA2_CAD_ACCELERATION` 값이나 현재 모델로 과거 실행을 소급 추정하지 않는다.

다음은 저장된 이전 실행을 재추출한 알고리즘 객체의 실제 값이다. 프로젝트·모델 ID는 없다.

```json
{
  "planner": "two_stage_general_first",
  "planner_version": "two-stage-learned-priority-v21",
  "recommendation_scope": "general_parts_only",
  "order_recommendation": {
    "method": "LGBMRanker",
    "prediction_calls": 8,
    "fallback_occurred": false
  },

    "method": "LGBMRanker",
    "prediction_calls": 9,
    "fallback_occurred": false
  },
```

### 11.7 실제 요약 기록의 성능·유사도 예시

문서 작성 때 기존 정확도 JSON 1건을 읽은 값이다. 새 대형 모델을 다시 계산한 벤치마크가 아니며 16장의 동결 test2 실행과도 별도 실행이다.

| 항목 | 실제 저장값의 표시 |
| --- | ---: |
| 생성 모드와 상태 | auto / CONFIRMED |
| 전체 생성 시간 | 128.8965276초 |
| Planner 시간 | 127.6904325초 |
| native 경로 시간 | 120.7627669초 |
| 후보 / 실제 path 호출 | 9 / 9 |

| --- | ---: | ---: | ---: | ---: | ---: |
| 전체 | 55 | 954 / 1,485 | 64.24% | 30/55 = 54.55% | 46/55 = 83.64% |
| 일반부품 | 14 | 60 / 91 | 65.93% | 9/14 = 64.29% | 9/14 = 64.29% |

| 서로 겹치지 않게 나눈 비교 | 전체 쌍 | 달라진 선후 쌍 |
| --- | ---: | ---: |

| 합계 | 1,485 | 531 |

달라진 531쌍 중 530쌍이 체결부 또는 예외 관련이다. 이는 체결부 500개가 잘못됐다는 뜻이 아니다. 체결부와 일반부품 간 쌍도 포함되며 체결부끼리인지 일반부품과의 비교인지는 현재 요약 집계만으로 더 나눌 수 없다. 동일 규격 체결부의 ID별 교환도 불일치가 될 수 있으므로 기능적으로 동등한 순서의 별도 지표가 구현됐다고 표현하지 않는다.

### 11.8 기록·재추출·오류 복구

`RunLog`는 원래 생성 파일의 잠금 하에서 수정한다. Windows에서는 msvcrt, 다른 환경에서는 fcntl 잠금을 사용하며 대기는 약 3초로 제한한다. 고유 임시 JSON → flush → fsync → 원자적 replace 순서로 저장한다.

상세 파일을 먼저 저장하고 독립 요약을 나중에 저장한다. 둘을 하나의 DB 트랜잭션으로 묶지 않는다. 외부용 폴더가 쓰기 불가이거나 다른 파일과 충돌하면 상세 기록과 DB 저장은 유지되고 `safe_log()`가 `LOG_WRITE_FAILED` 경고를 남긴다. 문제 해결 후 같은 생성/확정 기록이나 재추출 도구로 다시 만들 수 있다.

기존 로그의 일괄 재추출은 다음 소스 도구를 사용한다.

```powershell
.\.venv\Scripts\python.exe -X utf8 tools\export_accuracy_logs.py
.\.venv\Scripts\python.exe -X utf8 tools\export_accuracy_logs.py --log-dir "C:\대상\log"
```

`RunLog.export_existing()`는 해당 폴더의 `generation_*.json` 중 정확한 생성 로그 스키마만 처리하고 exported/failed/skipped 개수를 보고한다. 학습·이벤트 로그는 외부 파일로 변환하지 않는다. 기존 난수 ID를 재사용해 중복 파일을 만들지 않으며 원래 초안·확정 이력은 보존한다. 로컬 상세 로그에 대응용 난수 메타데이터만 추가할 수 있다.

이 일괄 도구는 개발용 Python 환경에서 실행하는 소스 도구다. 현재 EXE에 과거 로그 일괄 내보내기 전용 GUI 버튼이 있다는 뜻은 아니다. 일반 사용자의 이후 생성·확정은 별도 작업 없이 자동 기록한다. 현재 제공한 과거 로그 1건은 개발 작업에서 재추출했다.

### 11.9 외부 공유와 보안 경계

외부 요약에는 프로젝트명·차종·품종, 내부 프로젝트/부품/그룹/생성/확정/모델 ID, 부품명·형상, 실제 순서·방향 벡터·거리·좌표·카메라, 공정/자재/주의 문구, 경로·설정 객체·모델 데이터·오류 원문·생성/확정 시각을 넣지 않는다.

고정 키·엄격한 값 형식·열거값만 허용하므로 앞으로 상세 로그 필드가 늘어나도 자동으로 외부에 전달되지 않는다. 알 수 없는 알고리즘 버전 문자열도 허용 목록과 일치하지 않으면 `null`이다. UUID는 독립 난수일 뿐 원래 ID의 문자열 변경이나 단순 해시가 아니다.

그러나 통계적·법적 익명성을 보장하는 도구는 아니다. 부품 수, 예외 수, 시간과 여러 실행의 연관 패턴도 회사 규정상 민감할 수 있다. 파일 암호화·전자서명·중앙 반출 승인·자동 서버 전송은 구현하지 않았다. 외부에는 승인된 `log/accuracy_log/*.json`만 전달하며 상위 `log`, 프로젝트 DB, 모델과 원본 자료는 동봉하지 않는다.

## 12 영상 생성과 재생

### 12.1 확정본에서 프레임까지

```text
MainWindow._render
 → 미적용 입력·현재 계획 서명·확정 스냅샷 일치 확인
 → PlanService.load_confirmation
 → VideoRenderer.render / _render_once
   → build_timeline
   → select_encoder
   → VtkScene(offscreen=True).load
   → scene_at → VtkScene.apply → rgb_array → _compose
   → NumPy RGB 바이트 → FFmpeg stdin
 → MP4 완료 후 VideoPage.rendered
```

사용자가 순서나 방향을 바꾼 뒤 영상으로 만들 때 경로를 다시 검사하지 않는다. 확정된 계획 데이터의 형식과 현재 형상 스냅샷의 일치만 확인한다. 화면 녹화가 아니라 시간별 장면을 계산해 프레임을 생성한다. 부분 계획도 단계가 있으면 렌더링할 수 있고 누락 그룹은 임의로 사라지게 하지 않으며 부분 조립 문구를 표시한다.

### 12.2 시간축과 부품 이동

각 단계는 카메라 회전, 점멸, 조립 이동 구간으로 나뉜다. 롤을 포함한 자세 차이를 θ라 하면 다음을 사용한다.

```text
카메라 시간 C = θ ≈ 0이면 0, 그 외 max(0.3, camera_180_sec × θ/180)
단계 시간 = C + highlight_sec + assembly_move_sec
전체 시간 T = 단계 시간 합 + final_hold_sec
프레임 수 N = max(1, round(T × fps))
프레임 n의 시각 = n/fps, n = 0 … N-1
```

기본값은 180도 회전 3초, 점멸 2초, 이동 0.7초, 마지막 정지 2초다. 90도 카메라 전환이 있으면 기본 단계 시간은 `1.5+2+0.7=4.2초`, 전환이 없으면 2.7초다. 영상 재생 길이와 실제 생성 벽시계 시간은 다르다.

이동 진행률 `u∈[0,1]`에서 `f(u)=u²(3-2u)`를 적용하고 표시 오프셋은 `분해 방향 × 거리 × (1-f(u))`다. 시작에는 분해 방향으로 떨어져 있고 끝에는 조립 원위치에 도착한다. `vtkActor.SetPosition()`을 바꾸며 매 프레임 STEP나 BREP를 다시 만들지 않는다.

### 12.3 빨간 점멸과 이동 중 강조

점멸 구간은 `int(경과 시간×4) % 2`로 강조 강도를 1과 0 사이에서 전환한다. 약 0.25초마다 상태가 바뀌는 주기이며 이동 중에는 강도 1을 유지한다.

```text
표시색 = 기본 대표색 × (1-강조 강도) + 빨강 × 강조 강도
```

영상과 모델 재생은 같은 `scene_at()` 계산을 사용한다. 이 강도는 색 혼합 비율이지 Actor 투명도가 아니다. 영상에서는 전체 Actor opacity를 1로 복구하므로 편집의 회색 반투명·표시 오프셋·선택 오버레이가 영상에 섞이지 않는다.

### 12.4 고정 줌과 부드러운 카메라

AUTO는 단계의 조립 방향을 시선으로 사용하고 수동 카메라 모드는 고정 시선을 사용한다. 카메라 초점은 기준 부품 AABB 중심에 고정한다. 초기 완성 형상의 전체 범위를 기준으로 반경을 구하고 `max(반경×3.2, 100mm)` 거리로 유지한다.

```text
초점 = 기준 부품 중심 c
카메라 위치 = c - 시선 방향 × 고정 거리
```

이동 부품을 따라 `ResetCamera()`를 매 프레임 호출하지 않는다. 클리핑 범위는 갱신하지만 카메라 거리를 부품 이동에 맞춰 계속 확대·축소하지 않는다. 편집 화면의 명시적 맞춤 기능과 영상 카메라 정책은 구분한다.

카메라 시선과 화면 위쪽 벡터를 쿼터니언 자세로 변환해 SLERP로 보간하고 기본 smooth 모드에서는 진행률도 smoothstep 처리한다. 정반대 180도 전환과 롤 변화도 자세로 처리해 중간 영벡터나 화면 뒤집힘을 줄인다. `stepped_45` 호환 설정은 별도의 45도 단계 모드다.

### 12.5 화면 롤과 탑뷰 가로 정렬

`landscape_top_roll()`은 원래 완성 모델의 XY AABB에서 Y 길이가 X보다 길면 90도, 아니면 0도를 자동 기준값으로 정한다. 실제 탑뷰인 TOP 또는 AUTO의 -Z 시선에만 적용하고 사용자 `camera_roll_deg`를 더한다.

작업 속성의 좌우 버튼은 90도씩 화면 롤을 바꾼다. 표시 0도는 자동 가로 정렬 기준에 사용자 회전이 없는 상태다. PCA나 CAD 회전 최적화가 아니라 원래 AABB의 가로·세로 비교이며 모델 형상과 조립 방향은 바뀌지 않는다. 선택 단계 미리보기와 영상이 같은 자동 기준을 공유한다.

### 12.6 안내 템플릿

템플릿 버전은 `corporate-v3-compact-header`다. 최상단 프로젝트 정보에 도형을 추가하고 상·하단 및 모델 영역의 여백을 줄인 배치를 사용한다. 비율 좌표 `[x,y,w,h]`를 영상 해상도의 픽셀로 변환한다.

| 영역 | 정규화 좌표 |
| --- | --- |
| 상단 정보 블록 | `[0.015, 0.015, 0.74, 0.075]` |
| 3D 장면 | `[0.015, 0.105, 0.74, 0.80]` |
| 자재정보 | `[0.77, 0.105, 0.215, 0.39]` |
| 주의사항 | `[0.77, 0.51, 0.215, 0.395]` |
| 하단 과정 | `[0.015, 0.92, 0.97, 0.065]` |

기본 자재정보는 부품 표시명이다. 사용자가 빈 자재 문구를 유지해도 렌더링 시 해당 부품명으로 보완한다. 주의사항은 사용자가 입력한 내용만 출력하고 없으면 본문을 비운다. 내용이 비어도 패널 제목·테두리 등 템플릿은 남긴다. 자동 경고를 주의사항 텍스트에 끼워 넣지 않는다.

Pillow로 패널과 문구를 합성하며 글꼴과 같은 안내 오버레이를 캐시한다. 모델의 RGB 영역만 교체해 반복 레이아웃 부담을 줄인다.

### 12.7 MP4 인코딩과 완료 처리

기본 출력은 1920×1080, 30fps, H.264, yuv420p MP4다. NumPy RGB 배열을 `.tobytes()`로 변환해 FFmpeg rawvideo 표준입력으로 순차 전달한다. 전체 프레임 PNG를 먼저 디스크에 쌓지 않는다.

인코더 후보는 `libx264`, `h264_nvenc`, `h264_qsv`, `h264_amf`다. 각 인코더에 30프레임의 짧은 지원·시간 시험을 수행하고 auto에서는 지원 후보 중 시험 시간이 가장 짧은 것을 고른다. 이 짧은 시험이 모든 영상에서 최선임을 보증하지 않는다. 지정 하드웨어가 지원되지 않으면 소프트웨어로 대체하고, 하드웨어 인코딩 중 실패하면 전체 제한 시간 안에서 libx264 재시도 경로가 있다.

출력은 고유 임시 MP4에 기록한다. 취소·제한 시간 watchdog이 FFmpeg를 종료하고 완료 시 종료 코드, 파일 존재와 최소 크기를 확인한 후 최종 이름으로 변경한다. 기존 파일을 자동 덮어쓰지 않는다. 앱의 이 완료 검사와 테스트에서 수행한 전체 프레임 디코딩 검사는 별개다.

진행률은 생성 프레임 수 / 전체 프레임 수이며 대략 1초 분량의 프레임마다와 마지막에 갱신한다. 인코더 준비·메시 생성까지 포함한 전체 경과 시간 예측치는 아니다.

### 12.8 재생과 이전 영상 정리

영상 탭은 `QMediaPlayer`와 `QVideoWidget`을 사용한다. 처음·끝, 재생·일시정지, 앞뒤 5초 이동, 타임라인, 0.25·0.5·1·1.5·2·3·4배속, 전체화면과 Esc 해제를 지원한다. 모델 탭의 단계 이동과 영상 탭의 5초 이동은 서로 다른 동작이다.

영상은 프로젝트의 `videos`에 `<확정 ID>-<고유 접미사>.mp4`로 저장한다. `VideoLibrary.completed()`는 해당 프로젝트의 확정 ID와 연결되는 안전한 경로의 파일만 모으고 FFmpeg로 마지막 부분 프레임을 디코딩해 완료본을 확인한다.

최신 버전만 남기기는 파일 수정 시각 기준 최신 완료본 하나를 보존하고 이전 완료본만 삭제한다. 삭제 직전 최신 파일과 대상 파일의 변경 여부를 다시 확인한다. 다른 프로젝트, 외부 내보내기 사본, CAD, 순서 데이터, 임시·불완전 파일을 일괄 삭제하지 않는다. 내보내기는 해시를 확인한 복사이며 기존 목적 파일은 덮어쓰지 않는다.

설정에는 기존 확장용 `foreground_workers`, `background_workers`, `max_directions`, `memory_fraction` 같은 값도 남아 있다. 필드가 있다는 이유로 현재 모든 작업에 자동 병렬 배치나 60% 메모리 하드캡이 적용된다고 해석하지 않는다. 현재 유휴 학습의 별도 메모리 제한과 CAD 연산 스레드 제어가 실제 사용 경로다.

### 13.2 자동 epsilon과 메시 크기

초기 전체 AABB 대각선 D를 mm로 둘 때 다음을 적용한다.

```text
geometry_epsilon_mm = min(0.01, max(0.001, D × 10⁻⁷))
path_min_interval_mm = 같은 식
exit_clearance_mm = max(1.0, D × 0.005)
coarse_mesh_deflection_mm = max(0.2, D × 0.001)
display_mesh_deflection_mm = max(0.05, D × 0.0002)
```

표시 메시의 편차, 그룹화 재시도 허용치, 계산 형상 보정 수용치, 간섭 epsilon, 초기 체적 감소 허용 폭은 목적이 다른 값이다. 한 항목을 바꿨다고 다른 판정 기준이 자동으로 느슨해지는 것으로 설명하지 않는다.

`SettingsStore`는 사용자 데이터의 settings.json을 임시 파일로 저장한 뒤 교체한다. 일부 구버전 설정은 candidate timeout 180초를 240초로 이행한다. 설정을 바꿔도 기존 MP4나 이미 확정된 순서의 내용이 자동으로 다시 계산되지는 않는다.

## 14 작업 실행과 오류 처리

### 14.1 스레드와 프로세스 경계

1. UI는 전경 작업을 하나씩 받아 진행 메시지와 취소 상태를 표시한다.
2. 업무 작업은 QThread에서 실행하고 결과를 UI 스레드로 넘긴다.
3. `NativeCadSession`은 그룹별 계산 사본을 작업 디렉터리에 binary BREP로 저장한다.
4. `IsolatedCadWorker`는 spawn 방식 프로세스를 재사용하고 명령·결과·현재 네이티브 활동을 Pipe로 주고받는다.
5. 정밀 요청이 시간 초과·통신 실패·프로세스 종료이면 예외를 경로 UNKNOWN 등 진단으로 변환한다.

native timeout은 활동 메시지를 받을 때 갱신하는 네이티브 단계 제한이며 후보·전체 deadline과 함께 적용한다. 취소 시 협조 취소를 요청한 뒤 해당 프로세스를 종료한다. 일반 STEP 읽기처럼 같은 업무 스레드 안에서 실행하는 모든 C++ 호출까지 동일한 강제 종료 경계를 가진다고 보증하지 않는다.

### 14.2 대표 오류와 사용자 상태

화면의 작업 취소는 사용자 작업을 중단하는 기능이지 불완전한 결과를 검증 완료로 확정하는 기능이 아니다. 앱 종료 시 유휴 학습과 해당 자식 작업을 종료하고 전경 취소를 요청한다. 이전 실행에서 남은 DB 작업 상태가 RUNNING·CANCELLING이면 다음 실행 초기화에서 INTERRUPTED 실패로 표시할 수 있다.

## 15 배포와 제거 도구

### 15.1 배포 구성

사내 사용자에게 전달하는 파일은 `PA2_ver1_04_windows_x64.zip`이다. 압축을 전부 풀고 안의 `PA2_ver1` 폴더에서 실행한다. Python을 별도로 설치할 필요는 없지만 Windows 64비트, 쓰기 가능한 설치·데이터 폴더, 동작 가능한 그래픽 드라이버가 필요하다. 저사양 PC의 기능 실행 가능성과 일정 시간 안의 성능 보장은 구분하며 확정 최소 사양으로 인증한 시험은 아니다.

```text
PA2_ver1
 ├─ PA2.exe
 ├─ uninst.exe
 ├─ _internal/                       Python·Qt·VTK·OCP·모델·평가 리소스
 ├─ .pa2-install.json
 ├─ log/                             실제 사용자 로그는 포함하지 않음
 │   └─ accuracy_log/                초기에는 비어 있음
 ├─ 사용안내.txt
 ├─ V28_OPERATIONS.md
 ├─ docs/ACCURACY_LOG.md
 ├─ THIRD_PARTY_NOTICES/
 ├─ SHA256SUMS.txt
 └─ release-manifest.json
```

기존 프로젝트, 운영 DB, 개인 로그·영상, 개발용 src·tests·.venv·build는 배포에 넣지 않는다. 동봉된 합성 학습 참고 라벨과 평가 BREP는 운영 모델 리소스로 포함한다. 개발 PC의 설치 ID와 데이터 루트 등록은 새 배포용 설치 ID와 빈 data_roots로 대체한다.

현재 갱신본 ZIP은 329,995,391 bytes다. 설치 실행 파일 목록은 4,070개이며 안내·고지 등을 포함한 패키지 검증 목록은 4,194개다. 패키지 자체의 SHA256SUMS와 release-manifest는 자기 참조 해시 목록과 구분한다. 정확도 요약 기능이 있다는 것과 실제 사용자 성능 기록을 동봉한다는 것은 다르다.

PyInstaller는 one-folder 방식의 PA2 실행본을 만들고 uninst는 GUI·CAD 의존성을 불러오지 않는 별도 one-file 실행본으로 만든다. 패키징은 실행 파일과 `_internal` 전체의 해시가 설치 목록과 맞는지 먼저 검증한다. Qt 관련 VC 런타임을 같은 계열로 배치하고 Qt DLL 디렉터리를 명시하며, 이름이 같은 외부 ICU DLL 충돌을 피하는 런타임 경로 처리를 포함한다.

원래 개발 소스 파일을 배포하지 않는 것과 실행 파일의 역분석이 불가능하다는 것은 다르다. Python 모듈은 배포 실행을 위한 바이트코드 형태로 포함된다. EXE만 따로 떼어 전달하지 않는다. 전자서명과 별도 수신 PC 시험은 배포 확인 항목이며 동봉 고지가 외부 납품용 라이선스 검토 완료를 뜻하지 않는다.

### 15.2 설치 및 데이터 소유 등록

`.pa2-install.json`은 설치 ID, 프로그램 파일 상대 경로와 SHA-256, 등록된 데이터 루트를 가진다. `inventory()`는 PA2.exe, uninst.exe와 `_internal` 파일만 실행 관리 목록으로 만든다.

정상 앱 실행 시 `register_data()`는 설치 목록이 있는 경우에만 해당 사용자 데이터 루트를 등록하고 `.pa2-owned.json`에 설치 ID와 경로를 기록한다. 소스 체크아웃에 설치 목록이 없으면 제거 대상 등록을 하지 않는다. 처음 실행 전 제거하면 등록되지 않은 사용자 데이터를 자동으로 찾아 지우지 않는다.

### 15.3 삭제 범위와 절차

`uninstaller.main()` → `build_plan()` → 사용자 최종 확인 → 임시 helper 실행 → 부모 종료 대기 → `execute()` 순서다. 사용자에게 실제 설치·데이터 경로와 파일 수를 보여준다. 삭제 목록을 정렬해 승인 digest를 만들고 실제 실행 직전에 다시 계산한다.

| 대상 | 삭제 정책 |
| --- | --- |
| 설치 목록의 실행 구성 | 해시가 일치한 PA2.exe, uninst.exe, `_internal` 파일 |
| EXE 옆 log 바로 아래 | PA2 로그 스키마를 가진 JSON과 연결 잠금 파일 |
| log/accuracy_log | 정확히 `pa2-accuracy-log-v1` 스키마인 JSON만. 모르는 파일과 다른 하위 폴더는 보존 |
| 등록된 사용자 데이터 | projects, database, assets, cache, jobs, learning, logs, settings.json 및 소유 표식 |
| 외부 원본 STEP·제공 자료 | 대상이 아니며 삭제하지 않음 |
| 개발 소스·실험 기록·외부 내보내기 | 설치 관리 목록 밖이면 보존 |
| 변경된 실행 구성·미등록 파일 | 보존 또는 자동 삭제 거부 |

드라이브 루트·사용자 홈·Windows 같은 광범위 경로, 경계 이탈, 정션·심볼릭 링크, 소유 경로 불일치, 여러 설치가 등록된 공유 데이터는 차단한다. 같은 설치의 PA2와 CAD·학습 실행 프로세스가 있으면 먼저 종료를 요구하며 임의로 사용자 앱을 죽이지 않는다.

파일별 삭제 전에 경로를 검사하고 빈 디렉터리만 제거한다. 설치 루트나 사용자 루트에 재귀 삭제를 하지 않는다. 잠긴 파일 등이 있으면 실패를 알리고 재시도에 필요한 표식을 가능한 한 남긴다. 등록된 관리 자산 사본은 삭제되므로 외부 원본 보존과 프로젝트 복구 보장을 혼동하지 않는다. 삭제된 프로젝트의 복구는 보장하지 않는다.

설치 안내·고지 같은 미등록 파일과 임시 제거 helper가 남을 수 있으므로 폴더 안의 모든 흔적을 무조건 없애는 제거 도구는 아니다. 일반 삭제 시험은 운영 원본이 아닌 별도 복사본과 승인된 경계에서만 수행한다.

### 15.4 같은 버전의 갱신과 소스 전달 상태

이번 알고리즘 정보 추가는 배포 표기를 1_04로 유지했다. 따라서 같은 파일명이나 UI 이름만으로 이전 1_04와 최신 1_04를 구분하지 않고 부록 B의 EXE·ZIP 해시로 식별한다. 기존 설치 ID와 등록된 데이터 경로는 로컬 런타임 교체 시 보존했다. 이전 EXE·의존 파일과 이전 1_04 ZIP/체크섬은 개발 프로젝트의 build 백업에 보존했다.

현재 `PA2_ver1_04_full_source.zip`은 알고리즘 정보 로그 보완 **이전**에 생성된 소스 전달본이다. 사용자 요청으로 최근 작업에서는 EXE와 실행용 ZIP만 갱신했으며 전체 소스 ZIP은 다시 만들지 않았다. 현 소스 폴더와 최신 EXE가 일치한다는 검증을 이전 전체 소스 ZIP에도 적용해 해석하면 안 된다. 이 명세도 기존 ZIP 내부 문서를 자동 갱신하지 않는다.

전체 소스 ZIP은 개발용이므로 Python 3.13 x64와 잠금 라이브러리가 필요하다. 사내 실행용 ZIP은 의존 실행 구성이 포함돼 별도의 Python 설치가 필요 없다. 개발 시 `PA2_DATA_ROOT`, `PA2_DATABASE_URL`, `PA2_INSTALL_ROOT`를 시험 경로로 분리하고 `PA2_DISABLE_BACKGROUND_LEARNING=1`로 원하지 않는 재학습을 막는다.

### 16.4 유지보수 시 지켜야 할 인수 기준

1. 원본 STEP·제공 파일을 변경하지 않는다. 보정은 계산 사본에서만 수행한다.
