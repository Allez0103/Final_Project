## 1. 개요

### 1.1 프로그램을 구성하는 네 구조

PA²는 완성품의 STEP 형상을 분석하고, 분해 순서를 찾아 조립 순서로 변환한 뒤, 사용자가 편집·확정한 내용을 안내 영상으로 만드는 Windows 데스크톱 프로그램이다.

| 구조 | 핵심 질문 | 입력 | 출력 |
|---|---|---|---|
| 프로젝트 저장·관리 및 도면 분석 | 어떤 프로젝트의 어떤 형상을 사용하는가? | 프로젝트 정보, 완제품·부품 STEP | 분석 스냅샷, 부품 그룹, 접촉 그래프 |
| 자동 조립 순서 추천 | 어떤 부품을 어떤 방향으로 먼저 제거할 수 있는가? | 형상, 기준·예외 부품, 접촉 관계 | 조립 순서 초안, 판정 근거, 계산 지표 |
| 조립 순서 편집·확정 | 실제 작업에 맞게 어떻게 보완할 것인가? | 추천 초안 | 수정한 단계 목록, 확정본 |
| 영상 생성 | 확정한 조립 과정을 어떻게 시각화할 것인가? | 확정본, 형상, 영상 템플릿 | 조립 안내 MP4 |

### 1.4 화면이 멈추지 않도록 처리하는 구조

`MainWindow._task()`는 `TaskWorker`를 `QThread`로 이동시켜 분석·탐색·영상 작업을 실행한다. 진행 상황과 결과는 Qt Signal로 전달하고, `Qt.QueuedConnection`을 통해 화면 갱신을 UI 스레드에서 수행한다.

정밀 CAD 계산에는 별도 프로세스도 사용한다.

```text
UI 스레드: 사용자 입력·진행 표시·화면 모델 갱신
  ↓ QThread / TaskWorker
업무 작업: 분석 또는 순서 생성 흐름 실행
  ↓ NativeCadSession / IsolatedCadWorker.call()
CAD 자식 프로세스: CadDispatcher.execute() → Open CASCADE 호출
```

스레드는 화면 응답성을 위한 것이고, CAD 프로세스 분리는 긴 C++ 계산의 시간 초과·중단·비정상 종료를 관리하기 위한 것이다. 이 구조가 모든 후보를 동시에 병렬 검사한다는 뜻은 아니다.

## 2. 기능구현

### 2.1 3D 도면 저장 및 분석

#### 2.1.1 3D 도면 저장 구조 (DB)

##### A. DB와 파일을 분리하는 이유

STEP·BREP·MP4는 파일로 관리하고, SQLite에는 프로젝트 관계와 계산 결과의 관리 정보를 저장한다. 대용량 파일을 매번 DB 레코드에 넣지 않고, 해시·상대 경로·ID로 연결한다.

기본 저장 위치는 `DataLayout.default()`가 결정한다. `PA2_DATA_ROOT` 환경변수가 있으면 그 경로를 쓰고, 없으면 Windows 사용자 데이터 폴더인 `%LOCALAPPDATA%\THN\PA2`를 사용한다.

```text
데이터 루트/
 ├─ database/pa2-dev.sqlite3
 ├─ assets/<SHA-256>/source.stp
 │                  └─ manifest.json
 ├─ cache/shape/<캐시 키>/scene.json
 │                      ├─ bodies/*.binbrep
 │                      └─ complete.json
 ├─ projects/<프로젝트 ID>/planning/*.json
 │                        └─ videos/*.mp4
 ├─ jobs/
 ├─ learning/
 └─ logs/
```

##### B. 실제 저장 관계

| 테이블 | 저장 내용 | 연결 기준 |
|---|---|---|
| `projects` | 이름, 차종·품종, 리비전, 현재 분석·초안·확정본 ID | 프로젝트 ID |
| `assets` | 파일 해시, 관리 상대 경로, 크기, 종류 | SHA-256 |
| `project_assets` | 프로젝트별 입력 역할, 원래 파일명·경로, 리비전 | 프로젝트 ID + 자산 해시 |
| `import_snapshots` | 분석 시점, 준비 상태, 진단 | 스냅샷 ID |
| `atomic_bodies` | 솔리드별 체적·면적·중심·경계상자·유효성 | 스냅샷 ID |
| `part_definitions` | 부품 파일 정의와 특징 요약 | 부품 정의 ID + 자산 해시 |
| `assembly_groups` / `group_members` | 부품 그룹과 포함 바디 | 그룹 ID + 바디 ID |
| `contacts` | 그룹 쌍, 접촉 거리·근거, 정책 버전 | 스냅샷 ID + 그룹 쌍 |
| `grouping_structures` | 수동 그룹 계층과 원래 분석 스냅샷 | 스냅샷 ID |
| `planning_presets` | 기준 부품과 간섭 예외 부품 | 프로젝트 ID + 스냅샷 ID |
| `plans` / `plan_steps` | 초안과 각 단계의 방향·거리·문구 | 계획 ID + 단계 번호 |
| `confirmations` | 확정 당시 전체 계획 JSON | 확정본 ID + 계획 ID |

테이블에 정의된 모든 항목이 현재 GUI에서 적극적으로 쓰이는 것은 아니다. 예를 들어 `occurrences.color_json` 같은 스키마가 있어도 현재 STEP 색상 불러오기가 구현됐다는 뜻은 아니다. 현재 GUI 영상 파일 관리도 `projects/<ID>/videos`와 확정본 ID를 함께 이용한다.

##### C. SHA-256으로 입력 파일 식별

실제 호출:

```text
MainWindow._analyze()
  → ImportService.prepare()
      → AssetStore.ingest(완제품 STEP)
      → AssetStore.ingest(각 부품 STEP)
          → sha256_file()
          → 관리 사본 생성·해시 재확인
      → 분석·그룹화·접촉 계산
      → ImportService._persist()
```

`sha256_file()`은 1 MiB씩 파일을 읽어 해시를 갱신한다.

```python
# 핵심 구조를 줄인 예시
digest = hashlib.sha256()
while chunk := stream.read(1024 * 1024):
    digest.update(chunk)
checksum = digest.hexdigest()
```

파일명이 바뀌어도 내용이 같으면 해시가 같으므로 같은 관리 파일을 재사용할 수 있다. 복사할 때는 임시 파일의 해시가 원본과 같은지 확인한 뒤 최종 이름으로 바꾼다. 프로젝트별 원래 파일명·역할은 `project_assets`에 따로 남긴다.

##### D. 캐시 키와 BREP 복원

`cache_key()`는 입력 해시만이 아니라 단계명·알고리즘 버전·관련 설정·스키마 버전을 포함한 정렬된 JSON의 SHA-256을 계산한다.

```text
캐시 키 = SHA256(JSON(stage, inputs, stage_version, settings, schema_version))

형상 캐시의 예:
stage = "shape"
inputs = [STEP 파일 해시]
stage_version = StepImporter.VERSION
settings = {"unit": "file" 또는 지정 단위}
```

같은 파일이어도 분석 버전이나 관련 설정이 달라지면 다른 캐시를 사용한다. `CacheStore.publisher()`는 임시 디렉터리에 결과를 만든 후 `complete.json`을 기록하고 최종 경로로 옮긴다. `CacheStore.get()`은 이 완료 표식이 있는 결과만 반환한다.

`save_scene()`은 바디별 형상을 `BinTools.Write_s()`로 바이너리 BREP에 저장하고, 특징·ID는 `scene.json`에 저장한다. `load_scene()`은 JSON과 BREP를 결합해 `CadScene`을 복원한다.

기존 프로젝트 열기:

```text
MainWindow._reopen()
  → ImportService.reopen()
      → DB의 현재 스냅샷·바디·그룹·접촉 조회
      → 형상 캐시 load_scene()
      → 캐시가 없으면 관리 사본 STEP에서 재생성
  → PlanService.load_current_draft()
  → 저장된 확정본·설정과 현재 화면 연결
```

캐시 재생성 시 바디 ID 집합이 기존 스냅샷과 다르면 자동 교체하지 않는다. 기존 순서가 다른 바디와 잘못 연결되는 것을 막는 확인이다.

##### E. 트랜잭션과 확정본

`Database.session()`은 성공 시 `commit()`, 예외 발생 시 `rollback()`을 수행한다. 이는 DB 변경의 일관성을 위한 것이며 파일 작업까지 하나의 DB 트랜잭션이 되는 것은 아니다. 파일에는 앞서 설명한 임시 저장·완료 후 이름 변경 방식을 함께 사용한다.

`PlanService.confirm()`은 현재 `Plan.to_dict()`를 `confirmations.plan_snapshot_json`에 저장한다. 이후 초안을 편집해도 이전 확정본은 그 당시 내용을 가지고 있으며, 영상은 해당 확정본을 읽어 만든다.

발표용 설명:

> 파일 내용은 해시로 식별하고, 프로젝트·분석 스냅샷·조립 계획을 ID로 연결했습니다. 무거운 형상은 BREP 캐시로 복원하고, 확정 당시 계획은 별도 스냅샷으로 남겨 영상의 입력을 명확히 했습니다.

#### 2.1.2 3D 도면 분석

##### A. STEP에서 계산 가능한 솔리드까지

```text
ImportService.prepare()
  → StepImporter.read()
      → STEPControl_Reader.ReadFile()
      → FileUnits() / SetSystemLengthUnit(1.0)
      → TransferRoots() / OneShape()
      → TopExp_Explorer(root, TopAbs_SOLID)
      → _bounds() / _properties() / BRepCheck_Analyzer(..., False)
  → GroupingService.resolve()
  → ContactService.build()
```

길이는 mm 기준으로 변환한다. 파일 단위가 mm·inch 중 하나로 확인되지 않으면 단위 지정이 필요하며, 확인되지 않은 단위를 임의로 추정해 계산하지 않는다.

##### B. 체적·면적·중심·경계상자 계산

| 값 | 실제 호출 | 계산의 의미 |
|---|---|---|
| 체적 `V` | `BRepGProp.VolumeProperties_s()` → `Mass()` | 균일 밀도 기준 체적, mm³ |
| 표면적 `A` | `BRepGProp.SurfaceProperties_s()` → `Mass()` | 경계면의 면적 합, mm² |
| 체적 중심 `c` | 체적 특성의 `CentreOfMass()` | 균일 밀도 기준 중심 좌표 |
| AABB | `BRepBndLib.AddOptimal_s()` | 모델 좌표축에 평행한 최소·최대 범위 |
| 초기 유효성 | `BRepCheck_Analyzer(shape, False).IsValid()` | 기하 정밀 검사를 끈 초기 BREP 유효성 확인 |

수학적 의미는 다음과 같다. Python에서 직접 적분하는 것이 아니라 CAD 커널의 형상 특성 계산을 호출한다.

```text
V = ∫Ω dV
A = ∫∂Ω dA
c = (1 / V) ∫Ω x dV

AABB = [xmin, xmax] × [ymin, ymax] × [zmin, zmax]
크기 = (xmax-xmin, ymax-ymin, zmax-zmin)
대각선 D = √(크기x² + 크기y² + 크기z²)
```

그룹의 중심은 구성 바디의 체적 가중평균으로 만든다. 바디 체적이 20, 80 mm³이고 X 중심이 0, 10 mm라면 그룹 X 중심은 `(20×0 + 80×10)/100 = 8 mm`다. 그룹 체적은 바디 체적의 합이며, 겹침을 제거한 Boolean 합집합 체적과는 구분한다.

##### C. 자동 그룹화의 특징 비교

`GroupingService.resolve()`는 개별 부품 파일을 여러 바디로 이루어진 부품 정의로 만들고, 완제품 바디와 대조한다. 바디 수가 많은 정의를 먼저 처리한다.

`_body_match()`는 체적·표면적·정렬한 경계상자 세 변을 비교한다. 각 값 `a`, `b`의 허용 조건은 다음과 같다.

```text
|a-b| ≤ max(|a|, |b|, 1.0) × 상대 허용오차
기본 상대 허용오차 = 1e-4 = 0.01%
```

예를 들어 체적 1,000 mm³와 1,000.05 mm³는 차이 0.05 mm³가 허용량 약 0.100005 mm³보다 작아 체적 조건을 통과한다. 체적만 맞는다고 최종 매칭하지 않고 면적·크기도 확인한다.

다중 바디 부품은 `_find_matches()`에서 바디 중심 간 거리도 비교한다.

```text
δij = ‖ci-cj‖
|δij(부품 파일) - δij(완제품 후보)| ≤ 위치 허용오차
```

이를 통해 비슷한 바디들이 실제로 해당 부품을 구성하는 배치인지 확인한다. 후보 조합 수가 50,000개를 넘으면 과도한 조합 탐색 대신 미매칭으로 남긴다.

기본 매칭이 끝난 후에는 미매칭 바디만 재시도한다.

| 단계 | 특징 상대 허용오차 | 배치 비교 | 채택 조건 |
|---|---:|---|---|
| 기본 | 0.01% | `resolved_for_diagonal()`의 `geometry_epsilon_mm` 전달 | 서로 바디가 겹치지 않는 대응 채택 |
| 재시도 | 0.1% | 0.005 mm | 해당 정의의 후보가 하나이고 다른 정의와 경쟁하지 않을 때 |

`GroupingService` 생성자 자체의 위치 기본값은 0.05 mm지만, 현재 `ImportService.prepare()`는 모델 크기로 계산한 `geometry_epsilon_mm`를 명시적으로 전달한다. 발표에서 생성자 기본값을 실제 GUI 분석 설정으로 혼동하지 않도록 한다.

`GroupingResult.assert_partition()`은 모든 바디가 정확히 한 그룹에 속하는지 확인한다. 매칭되지 않은 바디도 단독 그룹으로 남기므로 누락시키지 않는다.

이 매칭은 특징과 배치에 기반한다. 경계상자 크기의 정렬만으로 임의 회전에서 완전히 불변인 형상 인식이 되는 것은 아니며, CAD의 제조 의미나 실제 체결 구조를 이해하는 방식도 아니다.

##### D. 수동 그룹화와 접촉 관계 재연결

`ManualGroupingService.change()`는 선택 그룹을 수동 그룹 노드로 묶고 새 분석 스냅샷을 만든다. 원래 자동 그룹은 하나의 잠긴 단위로 보존하며, 해제할 수 있는 것은 수동 그룹 노드다.

```text
선택 그룹 → composed_group() → 바디 목록·경계상자·중심 집계
          → 원래 접촉 그래프의 외부 연결을 새 그룹 ID로 재매핑
          → 새 스냅샷 저장 → 기존 초안·확정본의 현재 참조 해제
          → 새 그룹 구성으로 순서 재생성
```

그룹 내부 접촉은 외부 그래프에서 제거하고, 같은 그룹 쌍으로 합쳐지는 접촉은 하나로 집계한다. 체결부만 묶더라도 수동 그룹을 단순히 볼트·너트로 취급해 경로 검사를 건너뛰지 않도록 일반 탐색 대상으로 처리한다.

##### E. 접촉 그래프 계산

전체 그룹이 `N`개이면 가능한 무방향 쌍은 `N(N-1)/2`개다. 64개라면 2,016쌍이지만, 모든 쌍에 정밀 CAD 거리를 계산하지 않는다.

1. `ContactService.build()`에서 AABB를 접촉 간격만큼 확장해 가까운 쌍만 추린다.
2. 자식 프로세스의 `CadDispatcher.execute("distance", ...)`로 전달한다.
3. 솔리드·면 경계상자의 거리 하한을 이용해 먼 후보를 제외한다.
4. 꼭짓점의 내부·경계 분류로 접촉 증거를 먼저 찾고, 필요하면 `BRepExtrema_DistShapeShape`를 호출한다.
5. 거리값이 `contact_gap_mm` 이하인 그룹 쌍만 `ContactEdge`로 남긴다.

```text
축별 간격 gi = max(0, A의 최소-B의 최대, B의 최소-A의 최대)
AABB 거리 하한 = √(gx² + gy² + gz²)
접촉 판단 기준: 거리 ≤ contact_gap_mm (기본 0.05 mm)
```

이 경로는 접촉 여부를 위한 임계값 판단에 최적화돼 있다. 특히 내부·경계 증거를 찾으면 0을 반환할 수 있으므로, 모든 반환값을 고정밀 최소 거리 측정 결과로 해석하지 않는다.

접촉 그래프는 다음 단계에서 접촉면 방향, 볼트·너트의 연결 대상, 지지 관계 후보 등에 사용한다. 초기 교차 **체적**과 경로 허용 여부는 주로 2.2.1의 정밀 경로 검사에서 판단한다.

##### F. 표시용 메시와 계산용 BREP의 구분

`tessellate_shape()`는 `BRepMesh_IncrementalMesh`로 표시용 삼각형을 만든다. 면의 `TopLoc_Location` 변환을 정점에 적용하고, 뒤집힌 면은 삼각형 꼭짓점 순서를 바꿔 방향을 맞춘다.

`VtkScene.load()`는 그룹의 메시를 `vtkAppendPolyData`로 모으고 법선·Mapper·Actor를 연결한다. 따라서 여러 바디로 된 그룹도 하나의 Actor처럼 이동한다.

화면 표시에는 삼각형 메시를 쓰지만, 정밀 간섭 판단에는 BREP를 쓴다. 화면 메시가 거칠게 보이는 정도가 곧 정밀 CAD 판정의 정확도는 아니다.

발표용 설명:

> STEP의 솔리드에서 체적·면적·배치 특징을 계산하고 부품 파일과 대응시켜 이동 단위를 구성했습니다. 경계상자로 가까운 후보만 추린 뒤 BREP 접촉 계산을 수행해 부품 관계 그래프를 만듭니다.

### 2.2 조립 순서 자동 생성

#### 2.2.1 조립 순서 생성 원리

##### A. 전체 호출 흐름

```text
MainWindow._generate()
  → ImportService.ensure_contacts()
  → Planner.generate()
      → NativeCadSession.__enter__(): 그룹별 임시 BREP 준비
      → Planner._generate()
          → choose_base()
          → fastener_attachments()
          → 사용자 예외를 분해 선두에 배치
          → 볼트·너트의 축·머리 방향 힌트 확보
          → TwoStageSearch.run()
              → RemainingSetSearch.visit()에서 일반 부품 탐색 시작
              → 후속 visit() 재귀 / 후보 rank() / evaluate()
                  → ordered_v13(): 방향 우선순위
                  → worker.call("path", ...)
                      → CadDispatcher.execute()
                      → ConservativePathChecker.check()
          → 미해결 일반 부품의 편집용 초안 보완
          → 관련 볼트·너트 순서 삽입
          → 분해 순서 반전 + 방향 부호 반전
      → PlanningResult
  → MainWindow._planned(): 초안·진단 저장 및 화면 표시
```

`ordered_v13()`, `evaluate()`, `assigned_fastener()` 등은 `Planner._generate()` 안에 정의된 내부 함수다. 별도 공개 서비스 함수가 아니라 해당 실행의 캐시·상태를 공유하는 계산 함수다.

##### B. 일반 부품과 체결부를 분리하는 이유

현재 기본 제공자는 `TwoStagePriorityProvider`다. `TwoStageSearch.run()`은 볼트·너트를 정밀 탐색의 이동 후보와 장애물 집합에서 제외하고 일반 부품의 순서를 먼저 찾는다. 찾은 순서를 다시 전체 부품 대상으로 정밀 재탐색하지 않고 초안에 직접 사용한다.

```text
전체 그룹 = 기준 부품 + 일반 부품 + 볼트·너트
정밀 탐색 집합 = 기준 부품 + 일반 부품 - 사용자 지정 예외
최종 초안 = 일반 부품 초안 + 연결 관계에 따라 삽입한 볼트·너트
```

이 구조는 체결부 이동 경로의 물리적 가능성을 증명하는 방식이 아니다. 체결부 경로 검사를 생략해 추천 시간을 줄이고 사용자가 수정할 수 있는 초안을 만드는 현재 정책이다.

기준 부품은 사용자가 지정하며, 미지정 시 `choose_base()`가 유효 그룹 중 체적이 가장 큰 것을 선택한다. 기준 부품은 제거 단계에 넣지 않는다.

##### C. 부품 후보 우선순위: AABB 투영 노출도

`ExteriorPriorityProvider.direction_score()`는 방향별 가림 정도를 계산한다. 실제 가시 표면을 렌더링해 픽셀로 세는 방식이 아니라 경계상자의 투영을 사용하는 빠른 근사다.

방향 `d`에 수직인 두 축 `u`, `v`를 만들고, 경계상자의 중심 `c`와 크기 `s`를 각 축에 투영한다.

```text
투영 구간 중심 m = c·a
투영 반폭 r = (|ax|sx + |ay|sy + |az|sz) / 2
투영 구간 I(a) = [m-r, m+r]

대상 투영 면적 Ag = I(u)의 길이 × I(v)의 길이
가림 점수 coverage = Σ(상대 부품과 겹치는 투영 면적 / Ag)
보조 점수 count = 투영이 겹치는 앞쪽 장애물 수
```

가림 점수가 작을수록 바깥으로 열려 있을 가능성이 높아 먼저 시도한다. 예를 들어 투영 면적이 100 mm²이고 앞쪽 장애물의 겹침이 20, 30 mm²면 점수는 0.5다. 장애물끼리 겹친 투영 영역도 합산하므로 이 값은 1을 넘을 수 있으며, 정확한 노출 비율이나 확률이 아니다.

`rank()`는 6축 점수 중 가장 좋은 점수, +Z 방향 점수, 방향별 가림 합, ID 등을 순서대로 비교한다. 노출도가 같으면 위쪽이 열린 부품을 우선하는 보조 기준이 있다. 제거 후에는 잔여 부품 집합으로 다시 계산한다.

##### D. 분해 방향의 우선순위

일반 부품은 `GLOBALS`의 ±X·±Y·±Z 여섯 방향을 사용한다.

`direction_policy.policy_hint()`의 처리:

1. 현재 접촉 이웃과 초기 교차 체적을 확인한다.
2. 초기 겹침이 있거나 판정이 어려우면 노출도 기반 순위를 사용한다.
3. 그렇지 않으면 서로 마주 보는 평면을 찾아, 간격이 접촉 기준 이내인 면의 공통 영역 면적을 계산한다.
4. 가장 넓은 접촉면에서 멀어지는 법선 `n`을 방향 힌트로 반환한다.
5. 여섯 방향 중 `d·n`이 큰 방향부터 검사한다.

즉 접촉면 법선이 비스듬해도 그대로 임의 방향을 추가하지 않고, 6축 중 가장 잘 맞는 방향부터 검사한다. 한 방향이 경로·적용 지지 정책을 통과하면 즉시 채택하고 후속 방향 검사를 생략한다.

##### E. 이동 거리 계산

`exit_distance()`는 이동 부품과 잔여 장애물 전체의 AABB를 방향 `d`에 투영한다.

```text
pmin = 이동 부품 경계상자 꼭짓점의 최소 방향 투영
rmax = 잔여 장애물 합동 경계상자 꼭짓점의 최대 방향 투영
L = max(0, rmax-pmin) + exit_clearance_mm
```

예를 들어 +Z 방향에서 부품의 가장 낮은 점이 20 mm, 장애물의 가장 높은 점이 80 mm, 여유 거리가 5 mm라면 이동 거리는 `80-20+5 = 65 mm`다.

여유 거리와 수치 기준은 모델 대각선 `D`로 결정한다.

| 항목 | 현재 계산식 |
|---|---|
| 기하 판정 길이 기준 `ε` | `min(0.01, max(0.001, D×1e-7))` mm |
| 빠져나온 뒤 여유 거리 | `max(1.0, D×0.005)` mm |
| 경로 최소 구간 길이 | `min(0.01, max(0.001, D×1e-7))` mm |

`D=1,000 mm`라면 `ε=0.001 mm`, 여유 거리는 `5 mm`다. 이는 프로그램의 수치 판정 설정이며 제조 공차나 조립 여유를 직접 모델링하는 값은 아니다.

##### F. 정밀 경로 검사의 단계

`ConservativePathChecker.check()`는 한 부품의 한 방향 이동을 검사한다. 이동 형상은 `M(t)=M(0)+t·d`, 이동 범위는 `0≤t≤L`이다.

```text
입력 BREP 정밀 유효성 / 제한된 계산용 보정
  → 이동 전 구간 AABB와 겹치지 않는 장애물 제외
  → 장애물별 초기 교차 체적 확인
  → 초기 겹침 정책 또는 일반 연속 이동 영역 검사
  → 종점에서 상대 형상과 분리되는지 확인
  → PASS / BLOCKED / UNKNOWN 반환
```

| 판정 | 의미 |
|---|---|
| `PASS` | 현재 적용한 검사·예외 정책에서 해당 경로를 채택 가능 |
| `BLOCKED` | 실제 교차 또는 정책 위반의 차단 근거 확인 |
| `UNKNOWN` | 형상 생성·Boolean·시간 제한 등으로 결론을 내리지 못함 |
| `NOT_TESTED` | 예외 지정, 체결부 배치, 미해결 초안 보완 등으로 경로 미검사 |

초기 교차 체적과 특정 위치 교차 체적은 `_common_volume()`에서 `BRepAlgoAPI_Common`과 `BRepGProp.VolumeProperties_s()`로 구한다. 코드의 주요 체적 기준은 `ε³`다.

##### G. 초기 겹침 감소 허용 정책

현재 기본 설정은 초기 겹침 영역 예외와 감소 허용이 모두 켜져 있어, 초기 겹침 쌍에는 `_decreasing_overlap_extraction()`이 우선 적용된다.

```text
V0 = Volume(M(0) ∩ O)
Vk = Volume(M(sk) ∩ O)
허용 체적 변화량 τ = max(ε³, V0×1e-6)

Vk ≤ 지금까지 확인한 최소 교차 체적 + τ
```

검사 위치는 처음 `0.01, 0.05, 0.1, 0.25, 0.5 mm`, 이후 최대 0.5 mm씩 증가하며 최대 256개 위치를 확인한다. 허용량이 누적돼 겹침이 서서히 커지지 않도록 직전 값 대신 지금까지의 최소값을 기준으로 한다.

예를 들어 초기 체적이 100 mm³이면 `ε³`가 더 작다는 가정에서 `τ=0.0001 mm³`다. 검사값이 `100 → 80 → 20 → 0`이면 감소 조건을 만족하지만, `100 → 80 → 85`면 재증가로 차단한다.

교차 체적이 `ε³` 이하가 되면 남은 구간은 일반 연속 이동 영역 검사로 확인한다. 다른 비중첩 부품과의 경로 검사도 계속 수행한다.

다만 감소 구간은 위치별 표본 검사다. **같은 상대 부품에서 기존 겹침이 줄어드는 동안 다른 위치의 새 간섭이 생기는 현상까지 완전히 배제하지는 못한다.** 따라서 이 결과는 초기 감소 예외로 기록한다.

감소 허용을 끄고 초기 영역 예외만 사용하는 다른 경로는 다음과 같다.

```text
계산용 상대 형상 O' = O \ M(0)
전체 이동 영역이 O'와 새로 겹치지 않는지 확인
종점은 원래 상대 형상 O와 분리되는지 별도 확인
```

이는 원본 STEP를 잘라내는 작업이 아니라 계산용 형상에서만 초기 영역을 제외하는 정책이다. 두 정책을 동일한 보증으로 설명하면 안 된다.

##### H. 연속 이동 영역과 BSpline 처리

`_swept_check()`와 `sweep.enclosures()`는 이동 중 면이 지나가는 영역을 검사한다. `BRepPrimAPI_MakePrism`으로 면을 이동 방향·거리만큼 밀어낸 형상을 만들고, 상대 형상과의 교차를 확인한다.

평면 면이 이동 방향과 평행하거나 원통 옆면이 축 방향으로 움직이는 등 체적 이동 영역이 생기지 않는 경우는 별도 처리한다. 나머지 면의 이동 영역도 경계상자로 다시 걸러 필요한 교차 계산만 한다.

| 이동 영역 결과 | 처리 |
|---|---|
| 유효한 정확 이동 영역과 교차 체적 확인 | `BLOCKED` 근거로 사용 |
| 보수적으로 더 크게 잡은 영역과 교차 | 곧바로 실제 충돌로 단정하지 않고 미판정 근거로 사용 |
| 모든 필요한 포괄 영역이 비중첩이고 종점 분리 | 경로 통과 근거로 사용 |

BSpline 등의 곡면에서 직접 생성이 실패하면 UV 매개변수 영역으로 나눈다. 일반 곡면은 U·V를 각 4등분하는 구조이며, 원통·원뿔은 각도 구간과 투영 윤곽을 이용한 분할을 사용한다. BSpline의 UV 값을 라디안으로 해석하지 않는다.

분할된 곡면에서도 유효한 정확 이동 형상을 만들기 어려우면, 해당 패치가 지나가는 경계상자 솔리드로 보수적으로 둘러싼다. 이 상자와 부딪혔다고 실제 곡면의 충돌이 증명되는 것은 아니므로 `UNKNOWN`이 될 수 있다.

이때 실제 위치의 교차 증거를 찾는 보조 검사는 `BLOCKED`를 확정하는 데 사용할 수 있다. 단순히 몇 위치에서 안 부딪혔다는 이유로 `PASS`를 만들지는 않는다.

일부 경우에는 `_certify_interval()`의 거리 하한으로 연속 구간을 확인한다.

```text
구간 [a,b], 중간 m=(a+b)/2, 반길이 h=(b-a)/2
중간 위치의 실제 거리 δ(m) > h+ε 이면 구간 전체 분리
```

단위 방향으로 평행이동할 때 형상 사이 거리는 이동 거리보다 빠르게 감소할 수 없다는 성질을 사용한다. 판단이 안 되면 구간을 나누고, 최소 구간·시간 제한에서도 증명하지 못하면 `UNKNOWN`을 유지한다.

##### I. 입력 보정과 경로 형상 생성 오류의 구분

`prepare()`는 먼저 `BRepCheck_Analyzer(shape, True)`로 정밀 유효성을 확인한다. 초기 분석을 통과했어도 정밀 검사에서 곡선·매개변수의 불일치가 드러날 수 있다.

위상은 유효하지만 정밀 검사만 실패한 경우, 복사본에 `BRepLib.SameParameter_s()`를 적용하고 다음 조건을 모두 확인한다.

| 조건 | 현재 한계 |
|---|---|
| 보정 후 정밀 유효성 | 유효해야 함 |
| 최대 형상 허용오차 | 0.01 mm 이하 |
| 경계상자 좌표 변화 | `ε` 이하 |
| 면·모서리·정점 개수 | 보정 전후 동일 |
| 체적 변화 | `max(1e-9, 보정 전 체적×1e-5)` 이하 |

체적 상대 한계 `1e-5`는 0.001%다. 형상을 의도적으로 키우는 처리가 아니라 곡선 표현의 일관성을 보정하고 변화량을 제한하는 처리다.

입력 보정 통과 후에도 `MakePrism`의 이동 영역 생성이나 Boolean 연산이 실패할 수 있다. 입력 유효성 오류와 파생 경로 형상 생성 오류는 서로 다른 단계이므로, 앞 단계 수정만으로 모든 미판정이 사라지는 것은 아니다.

##### J. 잔여 상태 탐색과 중복 감소

탐색 상태는 제거 이력 전체가 아니라 `frozenset(remaining_ids)`로 표현한다. A 다음 B를 제거하든 B 다음 A를 제거하든 남은 부품이 같으면 이후 상태는 같다.

```text
현재 잔여 집합 R
  → rank(R)로 후보 우선순위 계산
  → evaluate(R, g)로 통과 방향 찾기
  → 통과: R' = R - {g}에서 재귀
  → 이후 막힘: 이전 선택으로 되돌아가 다른 후보 시도
```

현재 기본 제한은 되돌아가기 깊이 3, 횟수 100이다. 완전한 모든 순열 탐색이나 전역 최적 순서 탐색은 아니다.

| 재사용 수준 | 키 또는 조건 | 줄이는 계산 |
|---|---|---|
| 닫힌 상태 `closed` | 남은 부품 집합 | 같은 잔여 상태의 반복 탐색 |
| 그룹 평가 | 잔여 집합 + 부품 ID | 같은 상태의 동일 후보 방향 묶음 평가 |
| 정확 경로 캐시 | 상태 해시 + 부품 + 방향 + 거리 | 동일 경로 재요청 |
| 차단 근거 재사용 | 차단 장애물이 남아 있고 양 경로가 그 전체 투영 밖까지 도달 | 다른 상태에서도 같은 장애물로 막히는 계산 |
| 형상 쌍·체적·이동 영역 캐시 | 형상·방향·위치·거리·정책 등 | 반복 BREP Common·sweep 생성 |
| 방향 힌트 캐시 | 부품 + 현재 접촉 이웃 | 접촉면 방향 재계산 |

`closed`는 해당 실행 정책에서 후보를 충분히 탐색한 상태에만 기록한다. 시간 제한·조기 종료를 물리적 분해 불가능의 증거로 바꾸지는 않는다.

##### K. 볼트·너트의 연결 대상과 방향 배치

`fastener_attachments()`는 접촉 그래프에서 볼트·너트끼리 이어진 경로를 따라가 연결된 일반 부품을 찾는다. 여러 일반 부품과 관련되면 분해 초안에서 가장 먼저 제거되는 관련 부품을 소유 대상으로 정한다.

```text
일반 분해 초안: 커버 → 버스바 → 본체 부속
체결부 삽입:   커버 볼트 → 커버 → 버스바 볼트 → 버스바 → ...
조립으로 반전: ... → 버스바 → 버스바 볼트 → 커버 → 커버 볼트
```

사용자 예외 부품도 일반 분해 선택 목록에 포함되므로, 연결된 볼트·너트를 그 부품보다 앞에 삽입하는 같은 로직을 적용한다.

방향은 `direction_policy._fastener_hint()`와 `assigned_direction()`이 정한다.

- 볼트: 가장 긴 원통면을 축 후보로 삼고, 넓은 축 수직면·큰 반지름 원통면의 위치로 머리 쪽을 추정한다. 머리 방향이 확인되면 그 축 방향을 사용한다.
- 너트: 이미 접촉 관계에 있는 볼트의 축·머리 위치를 이용해 머리에서 멀어지는 방향을 우선한다.
- 힌트가 부족하면 연결 대상 중심에서 멀어지는 축 부호를 고르고, 축도 없으면 6축 위치 기반으로 결정한다.

방향 판정은 기존 면 특성과 접촉 정보를 사용한다. 머리 방향 추정 단계에 새 경로 검사나 접촉 Boolean 검사를 추가하지 않는다. 최종 체결부 단계의 경로 판정은 `NOT_TESTED`, 단계 상태는 `FASTENER_ASSIGNED`로 남는다.

##### L. 지지 관계·예외·전체 초안

경로가 통과하면 제거 후 남은 부품의 지지 경로를 `support_check()`로 확인한다. 기준 부품과 바닥에 놓인 부품을 출발점으로 하여, 아래에서 받치는 기하 접촉 관계를 통해 다른 부품으로 도달하는지 계산한다.

이는 기하학적 지지 연결 확인이다. 무게중심 안정성, 마찰, 공구, 체결력, 하중을 포함한 물리 시뮬레이션은 아니다. 현재 설정은 지지 미확인도 검토용 초안에 허용한다.

사용자 지정 예외 부품은 노출도가 가장 좋은 6축 방향을 즉시 배정하고 일반 경로 검사에서 제외한다. `USER_COLLISION_EXCEPTION`으로 구분한다.

일반 탐색이 끝까지 통과하지 못해도, 취소된 경우가 아니라면 채택한 앞부분을 보존하고 나머지는 `DRAFT_UNRESOLVED`로 초안에 채운다. 따라서 다음은 서로 다른 수치다.

```text
초안 단계 수 = 경로 채택 + 사용자 예외 + 체결부 배치 + 미해결 보완 등
경로 통과 단계 수 ≠ 초안 단계 수
```

최종 조립 변환은 `assembly_choices = reversed(best_choices)`와 방향 부호 반전으로 수행한다.

```text
조립 순서 = 분해 순서의 역순
조립 방향 = -분해 방향
```

#### 2.2.2 머신러닝 적용 (미구현)

##### A. 현재 구현 상태

현재 GUI 기본 추천은 `TwoStagePriorityProvider`를 사용하는 규칙·기하 기반이다. 학습 모델이 현재 화면의 기본 후보 순서를 결정하지 않는다.

다만 `FeatureBuilder`, `LearningService.capture()`, `LearningService.train()`, `LightGBMPriorityProvider.rank()` 등 학습 기반 코드는 있다. 따라서 ‘미구현’은 기반 코드까지 없다는 뜻이 아니라 학습 추천의 기본 운영 적용이 완료되지 않았다는 뜻이다.

##### B. 학습 데이터는 어떤 단위인가?

사용자 확정 조립 순서를 뒤집어 분해 순서로 만들고, 각 잔여 상태에서 실제 선택한 부품에 관련도 1, 다른 후보에 0을 부여한다.

```text
확정 조립 순서: C → B → A
분해 정답:     A → B → C

상태 R0의 후보: A(1), B(0), C(0)
A 제거 후 R1:  B(1), C(0)
```

`capture()`는 선택된 정답 순서를 따라 상태를 갱신한다. DB에는 `training_cases → ranking_states → ranking_candidates` 구조로 저장한다. 정답은 사용자 선호·확정 순서이며 그 자체가 CAD 경로 통과 증명은 아니다.

현재 GUI는 전체 단계가 있는 확정본이고 사용자 간섭 예외 단계가 없을 때 수집을 호출한다. 예외 부품만 빼고 나머지를 학습하는 방안은 앞서 논의한 향후 고도화 항목이며 현재 적용된 정책이 아니다.

##### C. 특징값 계산

`FeatureBuilder.rows(remaining)`는 부품과 현재 잔여 접촉 그래프에서 후보별 특징 행을 만든다.

| 특징 | 계산 예 |
|---|---|
| 정규화 크기 | 정렬한 AABB 변 길이 / 초기 모델 대각선 |
| 정규화 체적 | 부품 체적 / 초기 전체 그룹 체적 합 |
| 상대 중심 | `(부품 중심 - 초기 모델 중심) / 초기 대각선` |
| 기준 부품 거리 | `‖부품 중심 - 기준 중심‖ / 초기 대각선` |
| 접촉 수·비율 | 현재 이웃 수, 이웃 수 / `max(초기 N-1,1)` |
| 기준 부품 그래프 거리 | BFS로 구한 최단 접촉 연결 간선 수 |
| 잔여 비율 | 현재 부품 수 / 초기 부품 수 |
| 잔여 체적 비율 | 현재 그룹 체적 합 / 초기 그룹 체적 합 |
| 종류별 이웃 비율 | 해당 종류 접촉 이웃 수 / `max(초기 N-1,1)` |

면적·축·지지 특징 일부는 현재 `None`으로 남는 자리다. 선언된 모든 특징이 이미 정밀 계산돼 입력된다고 설명하지 않는다.

##### D. 학습·추론 호출

```text
학습 기반 코드:
LearningService.capture()
  → FeatureBuilder.rows()
  → 상태별 후보·정답 저장

LearningService.train(X, y, group_sizes, ...)
  → LGBMRanker(objective="lambdarank", ...)
  → fit(X, y, group=group_sizes)
  → 모델 + 특징·범주·버전·체크섬 manifest 저장

추론 기반 코드:
LightGBMPriorityProvider.rank()
  → rows(현재 잔여 상태)
  → NumPy 입력 행렬
  → Booster.predict()
  → 점수 내림차순 정렬
```

현재 학습 파라미터는 트리 300개, 학습률 0.05, 최대 리프 15, 목적 함수 LambdaRank, 평가 지표 NDCG다. 이는 후보 간 순서를 학습하는 설정이며, 출력 점수는 보정된 분해 성공 확률이 아니다.

`training_ready()`의 기본 준비 기준은 독립 형상 계열 30개와 순위 상태 1,000개다. 이 함수는 준비 여부를 판단하는 기반이며 `train()` 자체가 그 기준을 자동 검사·강제하는 것은 아니다. 현재 GUI에 자동 학습·기본 모델 적용까지 연결됐다는 의미로 설명하면 안 된다.

향후에는 `rank()`가 추천한 우선순위대로 기존 CAD 경로 검사를 수행하는 방식으로 연결할 수 있다. 모델은 검사 순서를 개선하고, CAD 계산은 경로 판정을 담당한다. 예측 오류나 비정상 점수 시 기본 순위로 돌아가는 기반도 있다.

발표용 설명:

> 향후에는 사용자 확정 순서를 상태별 후보 순위 데이터로 축적하고, 현재 잔여 구성에서 다음에 시도할 부품의 우선순위를 학습할 계획입니다. 전체 순서를 한 번에 확률로 예측하기보다 반복 검사의 순서를 개선하는 접근입니다.

### 2.3 조립 순서 편집/확정

#### A. 카드·부품·계획을 ID로 연결

`model_editor.py`의 `ModelEditor`는 기존 모델 화면을 확장해 가로 순서 카드와 작업 속성, 미리보기 기능을 제공한다. 카드의 `Qt.UserRole`에 그룹 ID를 저장해 화면 문자열 대신 ID로 `PlanStep`과 VTK Actor를 찾는다.

```text
카드 선택 / 3D 모델 클릭
  → 그룹 ID 확인
  → 부품 목록·순서 카드 선택 동기화
  → 작업 속성에 해당 PlanStep 값 표시
  → VtkScene.highlight()로 해당 Actor 강조
```

형상 미리보기는 `VtkScene.thumbnail()`의 오프스크린 렌더 결과를 카드 아이콘으로 사용한다. 선택·재정렬 때 기존 아이콘을 재사용할 수 있도록 보관한다.

#### B. 여러 순서의 묶음 이동

`SequenceCards.move_selection(to)`는 선택 카드를 현재 순서대로 정렬하고, 선택하지 않은 카드 목록 사이에 한 묶음으로 삽입한다.

```text
기존: [A, B, C, D, E]
선택: [B, D]
나머지: [A, C, E]
삽입 위치 2: [A, C] + [B, D] + [E]
결과: [A, C, B, D, E]
```

이후 `reordered` Signal이 `_reordered()`를 호출하고, `_commit_order()`가 카드 ID 배열대로 `plan.steps`를 재배열한다. `step_index`도 1부터 다시 부여한다. 선택한 B와 D의 내부 순서는 유지된다.

#### C. 방향·거리·문구 수정

`_apply_step()`은 속성 입력을 실제 단계에 반영한다.

```text
direction 콤보박스 → removal_direction
assembly_direction = -removal_direction
distance 입력 → travel_mm
camera 입력 → camera_mode
과정 / 자재정보 / 주의사항 → 각 텍스트 필드
plan.user_modified = True
```

UI의 축 선택은 내부적으로 `removal_direction`에 저장하고 조립 방향을 반대로 만든다. 발표에서 화면 축과 내부 필드의 부호 관계를 설명할 때 이 규칙을 따른다.

편집 경로는 `ConservativePathChecker.check()`를 호출하지 않는다. 사용자가 방향이나 순서를 수정하면 그 값을 받아들이고, 사용자 지정 예외를 제외한 해당 단계는 사용자 수정·미검사 상태로 관리한다.

실행 취소는 계획을 `copy.deepcopy()`한 이력으로 처리하며, 현재 UI는 최근 30개를 보관한다. 순서뿐 아니라 계획 필드의 이전 값을 복원한다.

#### D. 선택 단계 미리보기

```text
ModelEditor._preview_step()
  → 현재 Plan 깊은 복사
  → 아직 적용하지 않은 속성 입력을 복사본에 반영
  → build_timeline()
  → 선택 단계 시간 구간 선택
  → QTimer(33 ms) → _preview_tick()
      → scene_at(복사본, 시간)
      → VtkScene.apply()
  → 종료 시 기존 카메라·Actor 상태 복원
```

미리보기는 3D 장면을 시간별로 계산해 보여주는 과정이며 MP4를 먼저 만들지 않는다. 33 ms는 약 30회/초를 목표로 한 UI 타이머 간격으로, 실제 화면 재생 주기를 보장하는 값은 아니다.

#### E. 순서 확정과 변경 확인

`MainWindow._confirm()`은 적용하지 않은 속성 입력이 남아 있는지 확인한 후 `PlanService.confirm()`을 호출한다. `Plan.validate()`는 중복 부품, 기준 부품, 단계 구성과 데이터 형식 등을 확인한다. 이 검증은 CAD 간섭 재검사가 아니다.

`content_signature()`는 순번·그룹·분해/조립 방향·거리·시점·문구·최종 변환과 분석 스냅샷 등을 정렬 JSON으로 만들고 SHA-256을 계산한다. DB에서 정수가 실수로 복원되는 차이를 피하려고 거리와 벡터 수치를 `float`로 통일한다.

```text
확정 시 서명 Hc = SHA256(확정 계획의 비교 대상 내용)
현재 서명 He = SHA256(현재 편집 계획의 비교 대상 내용)
Hc == He이고 미적용 속성이 없음 → 영상 생성 가능
Hc != He 또는 미적용 속성이 있음 → 다시 적용·확정 필요
```

`matches_confirmation()`은 DB의 확정본을 복원해 실제로 비교한다. 따라서 앱을 다시 열어도 이전 확정 이후 편집 여부를 확인할 수 있다. 영상은 `load_confirmation()`의 결과를 입력으로 사용한다.

발표용 설명:

> 순서 카드와 3D 부품을 ID로 연결해 선택·묶음 이동·방향 수정을 동기화했습니다. 수정값은 공통 장면 계산으로 미리 확인하고, 확정 시점의 데이터를 따로 저장해 영상이 어떤 계획에서 만들어졌는지 관리합니다.

### 2.4 영상 생성

#### A. 전체 호출 흐름

```text
MainWindow._render()
  → 미적용 속성·확정본 일치·분석 스냅샷 확인
  → PlanService.load_confirmation()
  → VideoRenderer.render()
      → _render_once()
          → build_timeline()
          → select_encoder()
          → VtkScene(offscreen=True).load()
          → 프레임 반복
              → scene_at(plan, frame_index/fps)
              → VtkScene.apply()
              → VtkScene.rgb_array()
              → VideoRenderer._compose()
              → NumPy RGB 바이트 → FFmpeg 표준입력
          → 인코딩 성공 확인·임시 MP4를 완료 경로로 변경
  → VideoPage.rendered() / QMediaPlayer 재생
```

화면을 실시간 녹화하는 것이 아니라, 계획의 시간축에서 필요한 프레임을 계산한다. 영상 생성 경로에서 CAD 접촉·간섭 탐색을 다시 수행하지 않는다.

#### B. 시간축 계산

`build_timeline()`은 단계마다 카메라 이동 → 점멸 → 조립 이동 시간을 배정한다.

```text
이전·다음 카메라 방향 사이 각도 θ = acos(clamp(dprev·dnext, -1, 1))
카메라 시간 = θ가 0에 가까우면 0
              그 외 max(0.3, camera_180_sec×θ/180°)

단계 시간 = 카메라 시간 + highlight_sec + assembly_move_sec
전체 시간 T = 모든 단계 시간 합 + final_hold_sec
```

기본 설정은 180° 회전 3초, 점멸 2초, 이동 1.5초, 마지막 정지 2초다. 예를 들어 카메라를 90° 바꾸는 단계는 `1.5+2+1.5 = 5초`다. 회전 각도가 0인 단계는 기본적으로 3.5초다.

#### C. 부품 이동 위치 계산

이동 진행률을 `u∈[0,1]`로 두고 부드럽게 출발·정지하는 `smoothstep()`을 적용한다.

```text
f(u) = u²(3-2u)
이동 오프셋 Δp(u) = 분해 방향 d × 거리 L × (1-f(u))
```

`u=0`일 때 부품은 원래 위치에서 분해 방향으로 `L`만큼 떨어져 있고, `u=1`일 때 오프셋이 0이 되어 원래 조립 위치에 도착한다. 예를 들어 분해 +Z, 거리 100 mm라면 중간 `u=0.5`에서 `f=0.5`, 오프셋은 +Z 50 mm다.

이동은 `vtkActor.SetPosition()`으로 적용한다. 매 프레임 CAD 형상을 새로 계산하거나 STEP를 다시 읽는 방식이 아니다.

#### D. 점멸과 현재 강조 색상

`scene_at()`은 점멸 구간에서 `int(경과시간×4) % 2`에 따라 강조 강도를 0.85와 0 사이로 바꾼다. 약 0.25초마다 켜짐·꺼짐 상태를 바꾸므로 완전한 점멸 주기는 약 0.5초다. 이동 구간에서는 0.85를 유지한다.

`VtkScene.apply()`가 기본색과 강조색을 섞는다.

```text
표시색 = 기본색×(1-α) + 강조색×α
```

현재 영상 강조색은 노랑·주황 계열이며, 인터페이스 선택은 파랑 계열이다. 빨강으로 통일하는 요구는 보완 예정이다. 강조 강도 `α`는 이 코드에서 색 혼합 비율이고 Actor의 반투명도 설정값이 아니다.

#### E. 카메라 회전 보간과 줌 고정

`camera_for_step()`은 자동 모드에서 조립 방향을 시선 방향으로 사용하며, 사용자가 지정한 FRONT·TOP 등의 시점이 있으면 해당 방향을 사용한다.

`interpolate_camera()`는 방향과 화면 위쪽 벡터를 포함한 카메라 자세를 쿼터니언으로 바꾸어 구면 선형 보간(SLERP)한다. 아래 식의 `θ=acos(q0·q1)`는 쿼터니언 사이 각도이며, 시간축에서 사용한 실제 시선 회전 각도와 구분한다. `f`는 보간 진행률이다.

```text
q(f) = sin((1-f)θ)/sinθ × q0 + sin(fθ)/sinθ × q1
```

쿼터니언 내적이 음수면 부호를 바꿔 짧은 회전 경로를 선택하고, 두 자세가 거의 같으면 선형 혼합 후 정규화한다. 기본 부드러운 모드에서는 보간 진행률에도 `smoothstep()`을 사용한다. 정확히 반대인 시점과 롤 변화도 자세로 다뤄 화면 위쪽 방향이 갑자기 바뀌는 문제를 줄인다.

`VtkScene.apply()`는 기준 부품 경계상자 중심을 고정 초점으로 사용한다. 조립 원위치의 전체 경계로 정한 카메라 거리를 유지하며, 이동 부품을 따라 매번 화면 전체를 다시 맞추지 않는다.

```text
카메라 위치 = 기준 중심 - 시선 방향 × 고정 거리
카메라 초점 = 기준 중심
```

클리핑 범위는 갱신하지만 이동 부품 때문에 줌을 다시 맞추는 `ResetCamera()`는 프레임마다 호출하지 않는다.

#### F. 프레임 합성과 안내 템플릿

VTK 렌더 결과는 `vtkWindowToImageFilter`로 읽고 `vtk_to_numpy`로 RGB 배열에 바꾼다. 화면 좌표의 위아래 차이를 보정한 뒤 Pillow에 전달한다.

`_compose()`는 템플릿 JSON의 비율 좌표를 픽셀 좌표로 바꾸어 장면·차종·프로젝트·로고·자재정보·주의사항·과정 패널을 배치한다.

```text
픽셀 X = 템플릿 비율 X × 영상 폭
픽셀 Y = 템플릿 비율 Y × 영상 높이
```

자재정보가 빈 문자열이면 렌더 반복문에서 해당 부품의 표시명으로 채운다. 주의사항은 사용자 텍스트를 그대로 사용한다. 빈 주의사항도 `_panel()`은 테두리와 제목을 그리고, `_fit_text()`만 본문 그리기를 생략하므로 템플릿은 남는다.

프로젝트명·문구·영상 크기가 같은 프레임에는 안내 패널 캐시를 재사용하고 3D 장면 영역만 교체한다. 글꼴도 캐시하여 매 프레임 같은 배치를 다시 계산하는 부담을 줄인다.

#### G. 인코더 선택·프레임 전달·완료 처리

기본 출력은 1920×1080, 30fps, H.264 MP4다. 현재 출력 설정을 기준으로 다음을 계산한다.

```text
프레임 수 N = max(1, round(T×fps))
프레임 시각 tn = n/fps  (n=0,...,N-1)
완성 영상 길이 = N/fps
```

예를 들어 기존 v19 영상은 247.5초·30fps로 7,425프레임이다. 실제 생성 시간 205.855초는 영상 재생 길이와 별개의 벽시계 시간이다.

`select_encoder()`는 소프트웨어 `libx264`와 하드웨어 후보 `h264_nvenc`, `h264_qsv`, `h264_amf`에 짧은 인코딩 시험을 수행한다. 자동 모드에서는 지원 후보 중 측정 시간이 가장 짧은 것을 고른다. 이 짧은 시험이 모든 실제 영상에서 가장 빠른 결과를 보장하는 것은 아니다.

```text
NumPy uint8 RGB 배열
  → .tobytes()
  → FFmpeg stdin (rawvideo / rgb24 / 크기 / fps)
  → H.264 인코딩
  → yuv420p / MP4 / +faststart
```

모든 프레임 PNG를 디스크에 저장한 뒤 합치는 방식이 아니라 파이프로 순차 전달한다. 하드웨어 인코더로 인코딩 중 오류가 나면 같은 제한 시간 안에서 `libx264`로 재시도하는 경로가 있다.

파일은 임시 MP4로 생성하고 FFmpeg 종료 코드와 최소 파일 크기를 확인한 다음 완료 이름으로 바꾼다. 렌더 함수 자체의 이 확인과, 기존 통합 시험에서 수행한 전체 프레임 디코딩 검사는 구분한다.

진행률은 생성한 프레임 수 / 전체 프레임 수로 계산하며, 콜백은 대략 영상 1초 분량의 프레임마다와 마지막 프레임에서 갱신한다. 인코더 준비나 모델 메시 생성 전처리까지 모두 같은 비율로 나타내는 것은 아니다.

#### H. GPU 사용 범위

정밀 BREP 교차·거리 계산은 Open CASCADE의 CPU 계산을 사용하며, 지원 Boolean 연산의 병렬 옵션을 적용한다. 현재 CUDA 기반 CAD 간섭 계산은 없다.

VTK 3D 렌더링은 그래픽 드라이버/OpenGL을 사용하며, 실제 하드웨어 가속 여부는 실행 환경에 달려 있다. 영상 인코딩은 위 하드웨어 인코더가 지원되고 선택된 경우 GPU 또는 내장 그래픽의 영상 인코딩 장치를 사용할 수 있다. 전체 알고리즘이 GPU로 실행된다고 설명하지 않는다.

#### I. 영상 재생과 이전 버전 정리

`VideoPage`는 `QMediaPlayer`와 `QVideoWidget`으로 영상 미리보기를 제공한다. 배속은 `setPlaybackRate()`, 전체화면은 `setFullScreen()`, Esc 해제는 이벤트 필터로 처리한다.

`VideoLibrary.completed()`는 현재 프로젝트 폴더에서 해당 프로젝트의 확정본 ID와 연결되는 MP4를 찾고, FFmpeg로 마지막 부분의 프레임을 디코딩할 수 있는지 확인한다. `keep_latest()`는 파일 수정 시각 기준 최신 완료 영상을 남기고 나머지 완료본을 삭제한다. 내보낸 복사본과 다른 프로젝트 파일은 대상에 포함하지 않는다.

발표용 설명:

> 확정 계획을 시간축으로 바꾸고 각 프레임의 부품 위치와 카메라를 계산합니다. VTK로 3D 장면을 렌더링하고 Pillow로 작업 안내를 합성한 후 FFmpeg에 순차 전달하여 MP4를 만듭니다. 편집 미리보기와 영상이 같은 장면 계산을 공유합니다.

### 3.2 예상 질문에 대한 기술 답변

**“간섭은 화면의 삼각형으로 검사하나요?”**

화면에는 삼각형 메시를 사용하지만 정밀 경로 계산은 Open CASCADE의 BREP를 사용한다. 경계상자는 먼저 후보를 줄이는 데 사용한다.

**“순서가 끝까지 나오면 모두 분해 가능하다는 뜻인가요?”**

현재 결과에는 사용자 예외, 체결부 방향 배치, 미해결 초안 단계가 포함될 수 있다. 단계 수와 경로 판정·예외 상태를 함께 봐야 한다.

**“초기 겹침을 모두 무시하나요?”**

현재는 초기 교차가 있는 쌍의 겹침 감소를 위치별로 확인하고, 해소 뒤에는 연속 경로를 검사한다. 표본 구간에서 동일 상대의 국소 새 간섭까지 완전 배제하는 보증은 아니다.

**“기계학습으로 순서를 생성하나요?”**

현재 기본은 규칙·기하 기반이다. 상태별 후보 특징과 순위 모델의 학습·추론 기반은 있으며 기본 추천 적용은 향후 단계다.

**“수정하면 왜 다시 확정해야 하나요?”**

영상이 이전 확정 내용과 다른 편집값을 섞어 쓰지 않도록 현재 내용 서명과 확정본을 비교하기 때문이다. 다시 확정해도 CAD 간섭 계산을 다시 수행하는 것은 아니다.

**“동영상 화면을 녹화하는 건가요?”**

확정 계획의 시간별 장면을 계산해 프레임을 생성한다. 그래서 UI의 실시간 재생 속도와 영상 출력 길이는 별도로 결정된다.
